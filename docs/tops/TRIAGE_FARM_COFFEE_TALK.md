# Rethinking TRIAGE FARM over coffee

An artist first rendering and look review workspace for SYNAPSE

For Joe Ibrahim · 8 September 2026

Joe, I would keep yesterday's rendering engine and build a better creative experience around it. The useful idea in TRIAGE FARM is to spend a little render time answering a visual question before spending much more on the final image. SYNAPSE can make that feel like a natural part of lighting and look development.

If I were supervising a Houdini team, I would want an artist to open **Render**, see the shot they are working on, and have an obvious next action. Sometimes that action is rendering the current frame. Sometimes it is comparing a few roughness or lighting choices. Sometimes the decision is already made and the artist wants the sequence. Those activities should share the same scene history, results and job controls.

That is the best version of TRIAGE FARM I would aim for: **a dependable place to preview, compare and finish a look inside SYNAPSE**. TRIAGE remains the concept behind the experience. Render is the familiar front door. We can decide the final branding after using the first working version.

**Yesterday gave us the machinery worth keeping.** There is a direct Render entry, a modeless view, prepared scene packages, durable job records, detached local Houdini execution, cancellation handling and verified images. Jobs can be recovered without keeping the chat model involved. Sixteen images were verified in native Houdini 22.0.400 tests. That is a useful foundation, although the qualified fixtures are small Karma CPU renders and a multi-machine farm is still unfinished. The [implementation handoff](C:/Users/User/OneDrive/Documents/ChatGPT/SYNAPSE_Refactor/checks/tops-implementation/README.md) records those limits.

The old panel is helpful as a record of the idea. Its loader points to the separate project on G:, and its graph describes variations, proxy renders, image measurements and a contact sheet. I would carry that workflow into the new design while choosing the implementation from SYNAPSE's current architecture. The [source review](C:/Users/User/OneDrive/Documents/ChatGPT/SYNAPSE_Refactor/worktrees/tops-renderfarm/docs/tops/TRIAGE_FARM_MIGRATION.md) explains why its scripts and panel need to remain reference material.

**I would begin with one real visual question.** Suppose the shot feels too glossy. Keep the original look visible and try three explicit alternatives. Show the artist what changes and the total scope: four looks, one camera, one frame. A small deliberate comparison teaches us more about this interface than a wall of fifty random results. Larger searches can come later, when the artist has a reason to use them.

The original image should stay pinned. Alternatives should appear in stable positions as their verified renders finish. Picking a thumbnail should reveal its changed values. Enlarging it should preserve the same view transform, exposure and framing as the reference. If a render fails, its slot should say so; the grid should not quietly remove it or shuffle everything around.

There is real engineering behind that pleasant experience. Today's backend verifies the job's images at completion. For the first trial, each look can be a one-frame job, so its image enters the grid as soon as that whole child job passes verification. We can reuse yesterday's checks. Streaming individual frames from a larger unfinished job would require a further contract; the UI must never treat a half-written EXR as ready for review.

**The artist should choose the look.** The system can reliably identify a missing file, a corrupt image or a wrong output size. Measurements of darkness, sharpness or noise need interpretation. A soft, low-key shot may be precisely what you intended. I would show optional descriptive flags and keep every valid result selectable, while invalid results retain an explained slot. The prototype's suggestion that statistics can automatically discard a fixed share of bad images is not a rule I would carry forward.

The comparison should also look like the shot. The old prototype's scorer uses a fixed tone curve for EXRs. The new review view should use the shot's qualified color configuration, with consistent display settings across images. Denoising must be disclosed and consistent. A cheap preview needs enough information to support the decision; we should check that a chosen look still holds up at the intended final quality.

**TOPs is well suited to this, provided the work is explicit.** A Wedge TOP can generate variation attributes, and supported render workflows can pull those values or push them into target parameters. The important step is proving that the values reached the scene we actually rendered. The old wrapper mainly logs them. I would have the new system prepare a distinct frozen version of each look, then render those versions with recorded identities. SideFX also documents a selection-preview option that changes the interactive scene; the ordinary SYNAPSE thumbnail browser should remain observational. [SideFX Wedge documentation](https://www.sidefx.com/docs/houdini/nodes/top/wedge.html).

This gives us a clean division of responsibility. SYNAPSE understands the artist's request and preserves the job history. TOPs expresses which work depends on which other work. A qualified scheduler allocates machines. We can expose the generated graph to an experienced Houdini artist for inspection while keeping node paths and scheduler parameters outside the everyday flow.

**Choosing a preview and rendering the final need a careful handoff.** The selected look becomes the source of a new prepared render, with its exact changes carried forward. It must never silently pick up whatever happens to be in the current scene. Applying that look back to the editable shot is another explicit action, with a change preview and undo support. Selecting an image alone should leave the artist's scene untouched.

There is an important limit in yesterday's implementation: a preview package captures the requested frames and their dependencies. A package made for one frame does not establish that a whole animation is portable. Our first trial can compare one frame and render the chosen look at higher quality at that same frame. A later sequence needs a new preparation covering its frames, textures and caches, with any changed scene revision made visible.

**The interface should remember where you were.** Reopening Render should restore the job, original image, selected alternatives and useful context. A changed form should explain what needs preparing again. A lost connection should keep the job visible. One concise status and a useful recovery action are more helpful than a stream of technical notifications. Keyboard navigation, readable large text and a layout that works in a narrow Houdini pane belong in the first acceptance trial.

AI can help turn “try this a little softer” into a small, inspectable set of changes. It can explain an error or suggest which settings are worth testing. Once the scope is settled, rendering and recovery should work with the model disconnected. The artist's ordinary controls remain available while chat is busy.

**Before letting several jobs loose, I would add shared resource control.** Yesterday's limits apply to each job. Several individually bounded jobs can still compete for the same CPU, GPU or license. One admission owner needs to account for preparation, rendering and review work across requests. For a shared artist workstation, the chosen profile should leave measured room for interactive work. XPU needs its own device, memory and cancellation qualification; the old project's one-GPU settings do not establish that.

HQueue remains a sensible first adapter for a small Houdini farm. Its standalone graph mode separates the submitting session from graph execution, but the graph's scheduler, worker environment, storage and communications still need qualification. SYNAPSE's reconnectable progress must be built around that handoff. More machines should expand the capacity behind the same Render view. [SideFX HQueue Scheduler documentation](https://www.sidefx.com/docs/houdini/nodes/top/hqueuescheduler.html).

I would build this in usable steps: shared admission and trustworthy result cards; one original plus three real alternatives; selection carried into a same-frame final; then the same work distributed across two workers. Farm provisioning can proceed alongside the local comparison work. XPU and broader production scenes follow measured qualification. The early comparison trial is part of the plan, so we can learn whether it helps you before building a large search system.

My test as a supervisor would be practical: can you ask a visual question, make a choice, keep working, and later retrieve the correct result without reconstructing the job?
