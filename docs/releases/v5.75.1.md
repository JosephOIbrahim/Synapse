# v5.75.1 - The tag that was checked

**v5.75.0 was tagged on a commit whose CI concluded failure, and published five seconds after
its own run started.** This release supersedes it. The code in v5.75.0 was sound — the store
fix, the prune disarm, the memory wiring and the health surfacing all hold — but the tag was a
claim nobody checked, and this repository already has a script whose entire purpose is to stop
that.

## What was wrong with v5.75.0

- **CI-red on all four required contexts.** `VERSION` was bumped in four places and missed two:
  `CLAUDE.md` and the README banner. Three conformance tests read only repo files and fail on
  the drift — `assert '5.74.0' == '5.75.0'` — so the red is platform-independent. The repo ships
  `scripts/sync_version.py`, which prints the drift without running a test at all. It was not run.
- **The gate was skipped, not failed.** `scripts/release_ci_gate.py` exists because v5.64.0 and
  v5.65.0 already point at commits whose CI concluded failure, and v5.65.2 was tagged mid-run.
  This makes three. The script was not invoked.
- **Zero release assets.** v5.74.0 shipped an installer, checksums and two verification files.
  v5.75.0 shipped nothing, while the README download button still pointed at v5.74.0's asset.
- **A published figure that no CI leg produced.** The notes claimed
  `9620 passed, 433 skipped, 5 xfailed` "across the four required contexts". That is a local
  Windows / Python 3.14 number, and Windows is not one of the four. The real figure is
  `9461 passed, 485 skipped, 44 deselected, 4 xfailed`.

## What this release fixes

- **Version conformance across all six surfaces**, verified by `scripts/sync_version.py`
  (`verdict=PASS`) rather than by hand-counting. README download, checksum and release-note
  links now point at this version.

- **A write that overwrites stored data is no longer green.** Adversarial review reproduced the
  case: two records colliding on one id, the incoming one metadata-stripped, `add()` returning
  success, the richer record's tags and scene context gone — and all three health surfaces
  reporting OK with an empty reason. `health()` now carries `overwrote_prior`, counted only
  where prior data was actually replaced, and the write plane and panel strip both read it as a
  fault. It is deliberately **separate** from `rejected_writes`, which also rises on
  `add_durable_if_absent`'s correct idempotency refusal and would false-positive every deposit.

- **`health()` is asked before the property fast path.** The first attempt at the fix above
  landed in unreachable code: `_read_write_health` read the `is_degraded` property and returned
  before the dict branch, so for every real `MemoryStore` — which has that property — signals
  living only in the dict could never reach a verdict. A guard the real object cannot reach is
  not a guard.

- **Two shipped comments that were false against the code beside them** are corrected. The store
  claimed a write "is never quietly dropped"; routing means the *write* survives but the *prior
  record's metadata* does not, and the docs now say which.

## Verification

Pinned by a control in both directions: a store that overwrote data reads sick with a reason
naming the loss, and a clean store still reads green. A signal that is always red proves nothing.

`scripts/release_ci_gate.py` was run against this tag before publication.

## What this release still does NOT claim

Everything in v5.75.0's NOT-CLAIMED list stands: installing it does not repair an already-degraded
store, it does not change the whole-second id collision window, it does not recover a
pre-migration plaintext store, and it does not deposit mirror-only records into the primary.
