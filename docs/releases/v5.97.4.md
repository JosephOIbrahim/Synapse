## The short version

- **A native panic during a command now gets an answer.** When a native (Rust) extension panics while SYNAPSE runs a command, the caller gets a failed reply under its own request id, and the server answers the next request. Before, the panic passed every `except Exception` arm.
- **A panic in an automatic memory row no longer escapes.** With `SYNAPSE_AUTO_MEMORY=1` (off by default), a native panic while the session tracker writes one of its three automatic rows is logged, and that row is skipped. The session goes on, and so does the command's audit entry.
- **Also in the range.** Tests pin the coverage gaps the verifiers found in the two fixes. Two tests that flaked on the v5.97.3 CI run are hardened. The release card gets its corrections from the v5.97.3 cut. PR #115 rewrote the README's "Start here" and the status page's summary.
- **Not fixed here.** The panic is answered, not repaired. The connection handlers themselves still catch `Exception` only. Risk B, the automatic-consolidation residual and the sleep pass's undo-group routes stay open. Nothing in this range ran under hython.

## What changes

### A native panic at the dispatch seam (`274792c5`, L-PANIC-WS.1)

- **The bug.** PyO3 raises a Rust panic as `pyo3_runtime.PanicException`, which derives from `BaseException`. Every arm in `SynapseHandler.handle()` caught `Exception` or narrower, and so did `observe_operation` (`python/synapse/host/memory_loop.py`). The panic passed all of them.
  - On both WebSocket transports, no reply was sent.
  - On the in-Houdini `/mcp` endpoint and the panel's tool route, the panic escaped the tool call. What the HTTP layer sent next was not traced.
- **The fix.** One new arm after the last arm of `handle()` (`python/synapse/server/handlers.py:631`). A native panic is logged at ERROR with its traceback and answered with a failed reply under the request's own id and sequence. The reply's error reads:

  > A native (Rust) extension panicked while handling '&lt;command&gt;' (&lt;exception type&gt;: &lt;message&gt;). SYNAPSE kept running and answered this request. If Moneta's native module is loaded, MONETA_NATIVE=0 set before Houdini starts keeps it out.

- **What still propagates.** The arm re-raises everything `is_native_panic` rejects: `KeyboardInterrupt`, `SystemExit`, `GeneratorExit`, `asyncio.CancelledError`, a `PanicException` from another module, and any other `BaseException`. The classifier is imported lazily, as `handlers_memory.py` does. If that import fails, the arm logs it and re-raises the original exception, so the worst case is the old behavior.
- **Where it applies.** Both WebSocket transports (the standalone server's `_handle_message` and the hwebserver adapter's `receive`), the in-Houdini `/mcp` endpoint and the panel's tool route dispatch commands through `handle()`. Farm-control dispatch was not traced.
- **What it does not do.** SYNAPSE answers the panic; it does not repair the native module. A later call can panic again, and it is answered the same way. A failed reply does not mean nothing was written (see [Limits](#limits-that-remain)).
- **Left unchanged on purpose.**
  - The sleep-pass arm in `handlers_memory.py` still returns its own `ran=False` answer.
  - The WebSocket circuit breaker records a success only for a successful reply (`websocket.py:754-755` and `:878-879`). It records a failure before dispatch when the main thread is stalled (`:825-828`), and after dispatch only when an exception escapes as a service error or a timeout (`:900-901`). An answered panic moves neither count.
  - The wording names "a native (Rust) extension", never Moneta. `is_native_panic` matches every PyO3 panic, and `python/synapse/_vendor` ships PyO3 builds of `pydantic_core` and `jiter`.
- **The `MONETA_NATIVE` sentence in the reply.** `moneta_runtime._apply_native_kill_switch()` (`python/synapse/memory/moneta_runtime.py:174-215`) runs at `:226`, inside `_try_import()`, before its first `from moneta import` (`:228`, and the retry at `:239`). The only other Moneta import under `python/synapse` (`:786`) sits behind an `if not _MONETA_AVAILABLE: return` check. A module that something loaded earlier is left alone and reported as `already_loaded`; "before Houdini starts" puts the variable in place before the first Moneta import. The sentence helps only when the extension that panicked is Moneta's.
- **Test.** `tests/test_native_panic_dispatch.py` (new; fakes only; not run under hython). As `274792c5` adds it, 5 of its 11 cases fail on `545c13ee`, each because `PanicException` escapes. The 6 that pass there are pins: the six re-raise cases. With the arm, 11 of 11 pass. `a7eac233` adds 3 more (see [Test pins](#test-pins-a7eac233)).

### Automatic memory rows (`f5c92110`, L-PANIC-WS.2)

With `SYNAPSE_AUTO_MEMORY=1` (off by default), the session tracker writes three automatic rows: the session start, `Executed: <cmd>` and the session summary. Line numbers for the bug are at `545c13ee`.

- **The bug.** A Rust panic in any of those writes passed every `except Exception`.
  - In the start or summary row, it escaped `start_session` or `end_session` and then the connection handler (`websocket.py:595` and `:635`; `hwebserver_adapter.py:320` in `receive` and `:376` in `disconnect`).
  - In the `Executed` row, written by `log_action` and reached only from `handlers.py:653` inside `_submit_logs._do_log`, `run_on_main` re-raised the panic and the `except Exception` at `:657` missed it. `_do_log` stopped before the audit entry (`:659`) and the live integrity block (`:673-679`). The panic landed on a discarded Future (`:681`), and nothing was logged.
- **The fix.** Each of the three adds is wrapped (`python/synapse/session/tracker.py:187`, `:229` and `:383`). A native panic is logged at ERROR with its traceback, and that row is skipped. Anything else is re-raised unchanged.
  - `end_session` still returns the summary.
  - `log_action` falls through to `invalidate_context_cache()`, so `_do_log` goes on to write the audit entry and the integrity block.
  - The log reads: "A native (Rust) extension panicked while writing the session &lt;start|summary|action&gt; row (&lt;type&gt;: &lt;message&gt;); the row was not written and the session continues".
- **Test.** `tests/test_session_tracker_native_panic.py` (new; fakes only; not run under hython). As `f5c92110` adds it, 4 of its 5 cases fail on `545c13ee`, each with `PanicException` escaping. The 1 that passes there is the ordinary-error pin. With the arms, 5 of 5 pass. `a7eac233` adds 6 more.

**Across both files,** 9 of 16 new cases fail on `545c13ee` and the 7 that pass there are pins. That total adds two separate runs, one per fix commit, each on `545c13ee`. At the release tree the two files hold 25 cases, and all 25 pass when they run together in the Tier 2 full suite: 14 in `tests/test_native_panic_dispatch.py` and 11 in `tests/test_session_tracker_native_panic.py` (takeover record, the progress lines of `release/pytest_full_cut_a7eac233.txt`; summary in `release/targeted_full_cut_a7eac233.txt`).

## Limits that remain

### From this release

- **Answered, not repaired.** SYNAPSE answers the panic; it does not repair the native module. A poisoned native object can panic again on the next call, and each panic is answered the same way.
- **A failed reply does not mean nothing was written.** Work the command did before the panic stays. On the bridge routes, the failed reply sits inside the bridge's undo group, as any `Exception` does. A panicked operation's LOOP record stays pending, because `observe_operation` records exception evidence for `Exception` only.
- **The connection handlers still catch `Exception` only.** `websocket.py:607` and the hwebserver adapter's `receive` (`hwebserver_adapter.py:358`) and `disconnect` (`:379`) arms are unchanged. No Moneta call site found in this release's review reaches them.
- **The tracker arms are opt-in.** They guard the three rows written only with `SYNAPSE_AUTO_MEMORY=1`, which is unset by default. A caught panic drops one housekeeping row.
- **The pre-fix "no reply" was traced for the WebSocket transports only.** On the in-Houdini `/mcp` endpoint and the panel's tool route, the panic escaped the tool call. What the HTTP layer sent next was not traced.
- **Farm-control dispatch was not traced.** `execute_farm_control` (`websocket.py:864-866`; `mcp/tools.py:123-124`) calls `handle()` at `python/synapse/panel/bridge_adapter.py:235`, so the arm sits on that path too, but no test exercises it and its pre-fix behavior was not followed. This release's claims cover the four routes above only.
- **Automatic consolidation can store a memory and still report a failure.** `SYNAPSE_AUTO_CONSOLIDATE` is off by default, and the automatic pass has never fired in production (`python/synapse/memory/moneta_store.py:851-853`). With it on, a native panic during automatic consolidation escapes that `add()` before its cortex and JSONL mirrors are written (`:862` runs before `:870-871`). Inside a command the new dispatch arm answers it, and in an automatic session row the tracker arm logs it; other `add()` callers, such as `python/synapse/autonomy/driver.py:380` and `python/synapse/loop/ports.py:635`, were not traced. When a command triggered it, the reply says the command failed although the memory was already stored; retrying can store it twice (`python/synapse/memory/scene_memory.py:768-771`).
  - The arm for this path is designed but not built: after the `except Exception` at `moneta_store.py:1027`.
  - Whether automatic consolidation must also pass `SYNAPSE_ALLOW_SLEEP_PASS` is Joe's decision. Today it does not.
- **The sleep pass's undo-group routes are open.** On the in-Houdini HTTP `/mcp` route and the panel's tool route, an opted-in `synapse_sleep_pass` still runs inside the bridge's undo group (`execute_through_bridge`). The default refusal holds on every route, and the panel worker's DENY list refuses the tool by default. Routing the pass around the bridge, or accepting this as a residual, is Joe's decision. It is not recorded as accepted.
- **Not run under hython.** Both new test files use fakes only. Neither arm has run under hython, in a Houdini session or with the real Rust module. The 3.13 run used Houdini's bundled CPython as a plain interpreter, which is not hython.
- **The coverage gaps the verifiers found are pinned, with fakes.** `a7eac233` pins the classifier-import failure, the ordinary-error re-raise on the summary and action arms, `exc_info` on every arm, and `_submit_logs` with `enveloped=True` (see [Test pins](#test-pins-a7eac233)). Like the rest of the two files, these pins use fakes only.

### Carried from v5.97.3, still open

- **Risk B is not fixed.** Every save writes ECS rows and unlinks the WAL. Undrained attention is lost at the next store switch or quit, nothing drains it automatically, and the artist sees no error. The fix is planned for the next Moneta release. SYNAPSE's Moneta pin stays at `c33bbd96`.
- **The provenance version label can mislead.** With Moneta source on `PYTHONPATH` over an installed distribution, `_dist_version()` can label the source as the installed version (CTO F6).
- **CI shows that Moneta imports, not that the Rust extension runs.** CI has no Python 3.13 arm (F4). Locally, this release's 3.13 run gave 117 passed (see [Tier 2](#tier-2-the-integrated-tip)); it does not show the Rust extension running either.
- **The live seat is unchanged by this release.** D6b, which pins `MONETA_NATIVE=0` in the deployed package, waits for the landing window.
- **The receipts are local.** `private-recovery-records/` is git-ignored. The takeover citations in these notes resolve only in the maintainer's checkout. They do not ship with this repository.
- **The `child_category` field.** Consumers that reject unknown response fields need separate compatibility qualification (`docs/inspection-child-category.md`).
- **Held phantom rows.** `hou.cookPDGGraph`, `hou.pdg.workItem`, `hou.pdg.cookWorkItems` and `usdrender` are still held (see [v5.97.3](v5.97.3.md#limits-that-remain)).
