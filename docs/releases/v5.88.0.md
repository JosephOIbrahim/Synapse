# v5.88.0 — A failed call is flagged as an error, and Houdini is checked before a change

**A failed tool call is now flagged as an error.** The MCP specification says a
tool's own failure belongs inside its result, flagged `isError`, so that the
model can read it and correct itself. SYNAPSE did this on neither route. On
`/mcp` a failed tool arrived as JSON-RPC error -32603, and the stdio bridge that
Claude Code can use returned a failure as an ordinary result. Both routes now
return a result flagged `isError`. Its first line reads
`<outcome>: <message> Next: <next>`, and the whole outcome object is in
`_meta["synapse/outcome"]`.
[What a failed call tells you](../mcp/SETUP.md#what-a-failed-call-tells-you).

**Error codes -32006 and -32007 are withdrawn, one release after they shipped.**
In v5.87.0 a busy server answered -32006, and -32007 was reserved for a call
that needs an artist's approval. Both describe the outcome of a tool call, so
they now travel in its result. A busy server's result is flagged `isError`, with
the outcome `retryable` and the wait in `retry_after_s`. A client that matched
-32006 should read the result's outcome instead. -32007 was never sent.

**On `/mcp`, protocol failures stay JSON-RPC errors.** A request that cannot be
parsed, an unknown method, a call without a tool name, and a missing or expired
session still answer with JSON-RPC errors. A call to an unknown tool is now
refused there with -32602 before anything runs; the stdio bridge answers it with
a result flagged `isError`. Read-only mode keeps -32005, and its message is now
the outcome line.

**The SYNAPSE panel shows the outcome line.** When a tool fails, the panel shows
the same first line, and it never sends that call again.

**Houdini is checked before a change.** Before a session's first change, and
again after any retryable or unrecoverable outcome, SYNAPSE checks that
Houdini's main thread answers within 250 ms, that no scene is loading, and that
undo is on. On the stdio bridge it also checks that the bridge runs the same
SYNAPSE release as Houdini. A change that fails a check is not sent, and the
refusal names the fix: wait for the cook or the load, check Houdini for an open
dialog, run `undoctrl on`, or restart the side on the older release. Stop
controls, farm controls and reads are never held back by it, where a read is a
tool that read-only mode lets through. A ready answer is remembered for 10
seconds.
[Readiness before a change](../mcp/SETUP.md#readiness-before-a-change).

**`synapse_health` reports readiness.** It keeps its four fields and adds
`readiness`: `ready`, `degraded` (reads only) or `blocked`, with each check and
its status, whether read-only mode is on, and free disk and available RAM for
the open scene's folder and its `cache` folder. A figure that could not be
measured is `null`, never a guess. The check lives inside `synapse_health`
rather than in a new tool, so SYNAPSE still registers 137 tools.

**Restart the MCP client after you update.** The stdio bridge now sends its
SYNAPSE release with every command. A bridge started before an update, talking
to a Houdini started after it, has its changes refused until the side on the
older release restarts.

**Source release for Houdini 22.0.400 / Python 3.13.** No new Windows Setup is
included. The v5.86.0 Setup contains neither v5.87.0 nor these changes. Follow
[source installation](../getting-started/installation.md#source-installation),
then restart Houdini and any separate MCP processes to load the updated source.

## Validation and limits

Each change is pinned by tests that fail when it is reverted. The `isError`
results add 34 tests, and each of 14 deliberate reversions made one fail. The
readiness check adds 40 tests, and each of 24 reversions made one fail. Those
tests and the farm-control tests also passed in Houdini's own Python, hython
22.0.400: 80 passed, 1 skipped. The full `tests/` suite passed locally on Windows
with Python 3.14, with the tests that need a Houdini runtime deselected:
10,558 passed, 426 skipped, 119 deselected, 5 xfailed, 0 failed. The except ratchet is at 1,360 broad handlers and 983 silent ones, unchanged from v5.87.0. Publication requires all
six GitHub CI jobs to pass on the exact tagged commit, linked in the GitHub
release.

**Not checked live in Houdini.** The Houdini session on the release machine was
still running v5.87.0's code, and this release was published before a restart,
so neither change has run in a live Houdini session yet. The Houdini calls the
readiness check relies on were confirmed in hython 22.0.400:
`hou.hipFile.isLoadingHipFile()`, `hou.undos.areEnabled()`, and `undoctrl off`
and `undoctrl on` switching the latter.

**This closes three v5.87.0 limits.** A tool's failure on `/mcp` no longer
arrives as -32603, the stdio bridge flags its failures, and -32007 is withdrawn
rather than defined and unsent.

Some limits remain. The Level 1 blueprint's scene check, which refuses a change
once when a session has not seen the scene it is about to change, is not built.
The SYNAPSE panel does not run its own readiness check at the start of each
turn; the session check covers its first change. `synapse_health` measures free
disk on the scene's folder, and on a network share that does not answer, that
measurement can block. Every missed check counts toward the second-miss rule,
the ones `synapse_health` makes included, so polling it during a long cook can
make the next change's first refusal ask for the artist. Whether Claude Code
starts a new session by itself after a 404 has still not been observed, and the
panel's session recovery has still not been checked across a server restart.

The inherited [v5.87.0 limits](v5.87.0.md#validation-and-limits) remain, except
the three closed above.
