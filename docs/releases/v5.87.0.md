# v5.87.0 — MCP sessions recover, and every failed call says what to do next

**The SYNAPSE panel recovers an expired MCP session by itself.** The panel sends
its tool calls to Houdini's `/mcp` server. When that server restarted, or a
session expired after 30 idle minutes, the panel kept its old session, and every
call failed with "Unknown session" until Houdini's Python restarted. The panel
was checking for the wrong error code. It now starts a new session and sends the
call once more. A second refusal in a row is reported rather than retried, so it
cannot loop.

**`/mcp` answers a stale session the way the MCP transport specifies.** A
request without an `Mcp-Session-Id` header now gets HTTP 400, and an unknown or
expired session gets HTTP 404. A 404 tells a client that follows the MCP
specification to start a new session. Before, both got HTTP 200 with the error
only in the body, so such a client kept sending the dead session. The JSON-RPC
error body is unchanged, for clients that read only the body.

**The stdio bridge never sends a change twice.** Claude Code's stdio route
retried a command once when the connection dropped, even when the command had
already been sent, so a scene change could run twice. A command is now sent
again only if it never left, or if it is a protocol command, a stop control or a
tool that is read-only under both of SYNAPSE's gating sets. Otherwise the bridge
says the change may have run and was not sent again, and asks you to check the
scene first.

**Every refused or failed call says what happened and what to do next.** Every
call now ends in one of seven outcomes. A refused or failed call carries one of
the six besides ok: refused, retryable, unrecoverable, needs an artist, unknown
outcome or failed. Each comes with a stable code, a one-sentence message, the
next step in plain words, and whether the call reached Houdini: no, yes or
maybe. On `/mcp` the outcome is in the JSON-RPC error's
`data`; on the WebSocket it is in the response's `data`. The stdio bridge and the
SYNAPSE panel add the next step to the message they show. Send a call again
without looking only when it is retryable.
[What a failed call tells you](../mcp/SETUP.md#what-a-failed-call-tells-you).

**A busy server says how long to wait.** The rate limiter, the circuit breaker
and a stalled Houdini main thread used to answer with the generic JSON-RPC error
-32603. They now answer -32006, with the wait in `outcome.retry_after_s`.

**The stdio bridge names the fix when Houdini is not answering.** If it cannot
connect, it says nothing can succeed until something changes, and what to do:
start Houdini, open the SYNAPSE panel and click Connect. A timeout on a change is
reported as an unknown outcome, because the change may still be running; a
timeout on a read is retryable.

**Source release for Houdini 22.0.400 / Python 3.13.** No new Windows Setup is
included. The v5.86.0 Setup does not contain these changes. Follow
[source installation](../getting-started/installation.md#source-installation),
then restart Houdini and any separate MCP processes to load the updated source.

## Validation and limits

Each fix is pinned by tests that fail when it is reverted. The session and
resend fixes add 14 tests, and each of six deliberate reversions made one fail.
The outcomes add 20 tests, and each of seven reversions made one fail. The full
`tests/` suite passed locally on Windows with Python 3.14, with the tests that
need a Houdini runtime deselected: 10,483 passed, 426 skipped, 119 deselected, 5 xfailed, 0 failed. The except ratchet is at
1,360 broad handlers and 983 silent ones, unchanged from v5.86.0. Publication requires all six GitHub CI jobs to pass on the exact
tagged commit, linked in the GitHub release.

**Checked live in Houdini 22.0.400** by computer use, on the code in this
release:

- On `/mcp`, a request without a session header got HTTP 400 and an unknown
  session got 404, each with its outcome and next step. A notification got 202,
  and `tools/list` returned 137 tools.
- The panel's own client, given a session id the server had never issued, got
  the 404, started a new session, and its call answered.
- With `SYNAPSE_MCP_READ_ONLY=1` set in Houdini, a change was refused on `/mcp`
  (error -32005, with its outcome) and through the stdio bridge's own transport.
  Cancel cook passed the fence on both routes, and reads still answered. With the
  variable unset, the same change ran and failed on its missing node.
- The panel's **Identify** button, clicked with four nodes selected, drew the
  Identify chip and a bubble beside each node, and a second click cleared them.
  With 200 selected, it drew 60 markers, and the longest pause on Houdini's main
  thread was 81 ms, against 11 ms idle.

**This closes three v5.86.0 limits.** The 202 reply was checked on the live
server, read-only mode was checked live on both routes, and the Identify button
was clicked on the final overlay code.

Some limits remain. The panel's session recovery was checked by invalidating the
session on the client; a server restart with the panel open was not run live.
Whether Claude Code starts a new session by itself after a 404 has not been
observed. On `/mcp`, a tool's own failure still reaches the client as JSON-RPC
error -32603, now with its outcome, rather than as a result flagged `isError`,
the channel the MCP specification uses for tool failures. The stdio bridge still
returns a failed call as an ordinary result, not one flagged `isError`; its text
carries the outcome and next step. Error code
-32007, for a call that needs an artist's approval, is defined for the planned
cache guard and is not sent yet.

The inherited [v5.86.0 limits](v5.86.0.md#validation-and-limits) remain, except
the three closed above.
