# SYNAPSE v5.101.0

**The Render QC timing measurement lands, and it does not clear its budget.** A
four-part harness stages frames, times three passes per frame, decides under a
frozen rule, and emits a receipt that recomputes from its own per-frame values.
The verdict is **branch 4**: on the deciding tier the pipeline's floor — everything
except the dense analysis — is **5.732 s** against the **2.0 s** the frozen rule
carries, 2.9× over, while read plus write is only **0.300 s**. Making the dense
sites cheaper cannot reach the budget: they are **12%** of T on the deciding tier
(share **0.120**; **12–13%** of scan time), and the floor of **5.732 s** is what
remains once they are excluded. The other **~87%** of scan time is `S_rest`, a
residual bucket. Apart from two small pieces (one wrapped `cv2.dilate` call and the
wrapper's own overhead) its parts were never timed separately, so whether it is
reducible is unknown.

**One product change ships: the brain-stack import diagnostic.** When the
vendored SDK wheels are inactive on the running Python and the brain stack fails
to import, the error now quotes the exception it caught and says which of
`anthropic` and `pydantic` is actually installed, instead of asserting that
neither is.

**The release gates got stricter.** The tag script refuses without a committed crux
record bound to the reviewed code, and the release-notes guard checks the paths
named in the claims it judges against the tagged tree. Neither ships; both are how
this release is cut.

Every comparison in this note is against the v5.100.0 tag unless it names another
commit. The code it describes is `f50d9515`, the reviewed tip. The release commits add this note,
the CHANGELOG entry, the version bump, the README and logo refresh, and the crux
record the tag script requires.

## What changes for an installed seat

**One shipped code file changes: `python/synapse/host/daemon.py`, +36/−9.** It is
the only file `scripts/product_surface.py --diff v5.100.0 f50d9515` reports. The
release's version bump also rewrites the version string in shipped files
(`VERSION`, `pyproject.toml`, `python/synapse/__init__.py`, `docs/help/index.html`);
nothing else in the payload differs.

The change is confined to one branch: the import of `anthropic` raised
ImportError, and `synapse` has flagged its vendored SDK wheels (cp311 and cp313,
Windows) as inactive on this interpreter. Every other ImportError still raises
the existing "anthropic SDK is not installed" error.

- **Before:** that branch's error said no real `pydantic`/`anthropic` was
  installed. On the failure that prompted the change (commit `52f375e4`), both were
  installed and `anthropic`'s own import had died on a missing dependency, so the
  message asserted something false.
- **Now:** the error quotes the exception by type and text. It checks presence with
  `importlib.util.find_spec`, which does not import, and then says one of three
  things: both are installed and the failure is in a dependency of theirs; one is
  installed and the other is not; or neither is installed. The remediation text is
  unchanged.

**The timing harness does not ship.** Everything it adds is under `harness/`, and
`RUNTIME_TREES` in `installer/build_payload.py` — `python/synapse/`, `shared/`,
`houdini/`, `rag/catalog/`, `rag/corpus/`, `rag/skills/`, `rag/documentation/` and
`docs/help/` — contains no `harness/` entry.

**The release tooling does not ship either.** `scripts/`, `harness/`, `tests/` and
the root `conftest.py` are outside the payload. Everything under
[The release gates](#the-release-gates) and
[Developer side, not shipped](#developer-side-not-shipped) changes how SYNAPSE is
built and checked, not what a seat runs.

## The timing measurement

Every number in this section is recomputed from the committed receipt,
`harness/vision/qc_timing/timing_receipt.json`, with the harness's own
`decide.py`.

- **Verdict: branch 4, row 3, unanimous** across the three voting units: the
  deciding tier, char-9 and char-2. Producer: the receipt's `decision` block.
- **The branch-4 unanimity holds on exactly one band of budgets: B between
  0.3001815 s and 2.1958994 s.** Each edge is a unit leaving branch 4. Below the
  lower edge the deciding tier leaves first, because its own read plus write is
  0.300 s; above the upper edge char-2 leaves first, dropping to branch 5 and
  then, once B reaches its T of 2.30998605 s, clearing the budget outright. Once B
  reaches the tier's T of 6.4742666 s the deciding tier clears it too, so the
  verdict there is unanimous branch 1. The
  budget-independent statement is the tier floor: **5.732 s**, spread
  **5.335–7.709**. Producer: `decide.decide()` over the receipt's per-frame values,
  re-run at each B.
- **Deciding tier:** T **6.474 s**, R+W **0.300 s**, Floor **5.732 s**, dense
  share **0.120**. char-9: T 3.469, R+W 0.185, Floor 3.079, share 0.113.
  char-2: T 2.310, R+W 0.067, Floor 2.196, share 0.047 over 24 frames.
  Producer: the receipt's `decision.units`; every value is the median across that
  unit's conclusive frames.
- **char-2's Floor includes the harness's own bookkeeping.** The cv2 wrapper
  accumulates about **0.103 s** of overhead per pass inside the timed scan, and
  that overhead lands in `S_rest` and therefore in Floor. Subtracting each frame's
  median per-pass `overhead_s` from its Floor gives a median Floor of
  **2.0948 s** — still branch 4 at B = 2.0, but by **0.095 s** rather than
  **0.196 s**. More than half of char-2's margin over the budget is the measuring
  tool.
- **The run:** 541 records — 417 timed-pass records over 124 frames, 121 untimed,
  3 dry. **0 exceptions, 0 inconclusive frames, 0 check disagreements.** 45 of the
  timed records were voided, every one naming a foreign process caught in a process
  scan (`python.exe`, `python3.13.exe`, `hython.exe`, `husk.exe`): 30 at the scan
  before the pass, so that pass never ran, and 15 at the scan after it. 387 passes
  ran, and the 372 kept are three per frame. No voting unit lost its conclusive
  frames. Producer: the receipt's `frames`, `untimed` and
  `dry_pass` blocks.
- **The budget is an input to the measurement, not a result of it.** The 2.0 s
  constant is `B_SECONDS` in `harness/vision/qc_timing/decide.py`, part of frozen
  rule revision 2 (`B = 2.0`, `threshold = 0.5`), and the receipt records the same
  values in its `rule` block. Every figure above was computed against that 2.0 s.
  Whether 2.0 s is the right number was owner decision QC-Q3; Joe ruled on
  14 November 2026 to keep it.
- **The receipt reproduces its own decision.** `decide.decide()` over the
  receipt's per-frame values returns a dict identical to the receipt's `decision`.
  The raw pass records the receipt was composed from are not published, so this
  note cites only what the committed receipt can show.
- **The receipt file carries no frame names and no workstation model strings:**
  no `cpu_model` and no `scratch_drive_model` key anywhere in the document.
- **Closure predicate:**
  `harness/next-release/proposals/predicates/test_nr_qc_timing.py`,
  **36 passed** at `f50d9515`.

## The release gates

**The tag script refuses without a valid crux record.** `scripts/tag_release.py`
now requires `harness/notes/release-<version>/CRUX-RECORD.json`, committed in the
commit being tagged, naming this version, marked passed, and covering a
`<base>..<tip>` range of commits. It refuses when:

- the record is absent, unreadable, incomplete, for another version, or not passed;
- the range is written backwards, is empty, or changes no files;
- the reviewed tip is not in the history of the commit being tagged;
- the review is dated before the reviewed tip or after today;
- **any file the reviewed range changed is different at the tagged commit.** Files
  outside the range may still change after the review, which is how the notes, the
  CHANGELOG entry and the version bump land; files inside it may not, whether code
  or docs. Renames count as changes.

The script also captures HEAD before any check runs, names that commit in the tag
command, and refuses if HEAD is no longer that commit when the checks finish. Its git calls no longer
inherit `GIT_DIR` or the other repository-location variables, so a leaked variable
cannot point the gate, or the tag, at another repository.

**The release-notes guard checks paths against the tagged tree.** In
`harness/jev/jev_release.py`, a judged claim naming a repo-relative path that is
absent from the tree of the tag being judged is UNSUPPORTED whatever the model
scored, and the guard prints the missing path. The check reads the tag's committed
tree, never the working directory. A tag that does not resolve is refused before
the model is asked. Two limits: the guard judges at most 20 paragraphs after the
note's first `##` heading, and it recognises a path only when the token has a
directory and a file extension. Separately, the verdict rule it already applied
inline at v5.100.0 now lives in one function, `classify_claim`, with the same
thresholds read from the policy.

**This release's crux review.** Codex reviewed `v5.100.0..f50d9515` and passed it
on 14 November 2026; the record is `harness/notes/release-5.101.0/CRUX-RECORD.json`.
Its first review, of `7d5d6e7d`, failed on one finding: a test carried a real local
account path, which the source-archive audit that qualifies a release rejects.
`f50d9515` replaced it with a placeholder, and the audit then returned 0 findings.

## Developer side, not shipped

- **Every pytest run stamps what it measured.** A `synapse identity:` header line
  carries the commit, the interpreter with a short hash of its path, and which of
  `numpy`, `cv2`, `mcp`, `pxr`, `PySide6`, `anthropic` and `pydantic` are present.
  The commit is read from the repository the root `conftest.py` belongs to, not
  from wherever pytest was started.
- **The suite ratchet refuses to compare across interpreters.** It returns
  `INTERPRETER MISMATCH` before running when the interpreter differs from the one
  the baseline was recorded on.
- **Four panel Qt test files no longer need pytest in their `-I` child.** The child
  used to die on `No module named 'pytest'` wherever pytest lived in the user site;
  by commit `df69f93b`'s own count that was 118 of 152 non-passing outcomes in a
  local baseline. CI never saw it. Where PySide6 is absent, as on that machine and
  on CI, those probes now skip rather than error, so they still measure nothing
  there. Two of those files also drop `-I` when run under hython, whose stdlib
  bootstrap it breaks.
- **The real-probe daemon diagnostic test keys on the outcome it observes.** It
  asserts the diagnostic when the import really fails, skips when it cannot
  produce a real failed import on the machine it runs on, and fails on any other
  outcome.
- **`harness2 --out` writes the file it reports.**
- **The timing harness test feeds sentinel strings, not real hardware strings.**
  The test that keeps workstation model strings out of the receipt now proves it
  with fixed sentinel values (commit `771b4c73`), so the test no longer carries a
  real machine's model strings itself.
- **`TAGS.md` names v5.100.0.**
- **Test isolation.** The release-guard tests run when their file runs alone, and
  the Identify salience tests no longer inherit the `SYNAPSE_JEV` kill switch from
  the environment.

## Limits

- **No artist sees a finding from the timing harness.** It is a measurement tool
  under `harness/`; nothing in the product calls it.
- **The budget stays at 2.0 s.** The constant is in the frozen rule and every
  timing figure is computed against it. Owner decision **QC-Q3**, ruled by Joe on
  14 November 2026, keeps it. At that budget the measured pipeline does not fit:
  the deciding tier's floor is 5.732 s.
- **The import diagnostic has rare failures of its own.** Three are known, and
  the fixes are planned for the next release:
  - If `anthropic` or `pydantic` is already in `sys.modules` as a stub module
    without an import spec, the presence check (`importlib.util.find_spec`)
    raises `ValueError`, and that error replaces the diagnostic message. Nothing
    in SYNAPSE installs such a stub today.
  - An import finder that raises from `find_spec` replaces the diagnostic the same
    way. The crux review reproduced it with a synthetic finder.
  - Finding both modules does not prove that a dependency failed. A local file
    named `anthropic.py` that shadows the package makes the message blame a
    dependency when the cause is the shadowing file.
- **The crux review found four defects in this release's developer-side code.
  None touches the shipped code or the measured results.** The fixes are planned
  for the next release:
  - When a timing run resumes, the harness forgets the timed exceptions it already
    recorded, so a second exception on a frame does not stop the run. The committed
    receipt has no exceptions.
  - The timing closure predicate rejects a valid resumed frame, because it keeps only
    the frame's latest warm-up. The committed receipt passes it.
  - The tag script checks HEAD at the end, not between its checks, so a concurrent
    checkout that moves HEAD away and back could have it check one commit and tag
    another. One conductor at a time is the guard.
  - The pytest identity line prints a dependency it could not probe as absent.
- **The timing data is one run on one machine.** 124 frames, one host, with 45
  passes voided for foreign processes.
- **Durable worker receipts are not in this release.** That lane waits on its own
  review and is not merged.
- **The timing branch is merged twice.** `19a2fb74` and `db8b43a6` both merge it:
  the receipt was rebuilt between the two merges, and the tree at `f50d9515`
  carries only the rebuilt one. Producer:
  `git log --merges --format='%h %p %s' v5.100.0..f50d9515`, which lists 17 merges
  in all.
- **Leg C's uninstall-registration precondition fails on this machine.** Its
  check `production_uninstall_registration_absent_before` has failed here since
  the 2026-11-09 live install created the per-user uninstall registration. By
  Joe's ruling of 14 November 2026, the same as v5.100.0's, that single check
  failing is a known machine precondition for the v5.101.0 Setup
  qualification, not a release red; any other leg C failure is a red. This
  release's leg C result is in its verification record, a release asset of the
  `v5.101.0` tag.
- **anthropic 2.x remains unsupported.** The pin stays `anthropic>=1.0.0,<2` in
  `pyproject.toml`.
- **Setup remains unsigned.**
