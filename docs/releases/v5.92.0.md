# v5.92.0 — H22 Solaris workflows build in one call, a wrong node type names the real one, and REVERT undoes only SYNAPSE

**Verified recipes for three H22 Solaris workflows.** Asked for three workflows
from Rob Pieke's Houdini 22 Solaris talk, the panel agent built none of them on
v5.91.0: it guessed node type names, or fell back to the pre-H22 way of doing
the job. `python/synapse/routing/solaris_recipes.py` now holds three verified
recipes, each one `synapse_solaris_build_graph` call that splices new LOPs into
an existing chain:

- **Scatter Instances on a surface, masked to a camera.** A Gaussian-splat
  world has no mesh to scatter on, so the recipe references the world's collider
  under the world prim, hides it with Configure Primitive, adds a prototype, and
  runs `scatterinstances` with the camera mask on. It splices in after the node
  that authors the camera, because the mask reads the camera prim.
- **A Karma blocker light filter bound to a light.** `karmablockerlightfilter`
  with its shape set, and a `light` whose light-filter parameter targets it,
  which authors the light's `light:filters` relationship.
- **Render Pass LOPs.** Two `renderpass` nodes, one with a render-visibility
  pattern that keeps one prim and the lights, spliced in before the render
  settings node.

**The artist's words reach the recipe.** `synapse_knowledge_lookup` returns the
matching recipe, with its notes, its placeholders and its payload, when a query
names the workflow: "karma blocker", "light filter", "scatter instances",
"render passes", and the spellings the model used on v5.91.0. A query that is
only a node type name still returns that type's datasheet, which now points to
the recipe. The system prompt names the three types and asks for one lookup
and one build call.

**A wrong node type names the real one.** `houdini_create_node` used to answer
an invalid type with Houdini's bare "Invalid node type name". It now answers
with the closest real types in that network's category, taken from the running
build's catalogue with hidden and deprecated types left out, or says that
nothing is close and to look up the artist's words. `build_graph`'s rejection of
an unknown type lists the closest real types too, and points at
`synapse_knowledge_lookup` instead of `synapse_scout`, which the panel worker's
allowlist does not permit.

**USD reads at the current frame.** `houdini_get_usd_attribute` read every
attribute at USD's default time. Configure Primitive writes visibility as a time
sample at the current frame, so an invisible prim read back as `inherited`. The
read now uses the current frame; an attribute with no time samples reads the
same as before.

**The panel.**
- **REVERT undoes the last turn itself.** It used to send a new turn to the
  model. It now undoes that turn's undo entries directly, but only when every
  one carries a SYNAPSE label and they are still on top of the stack exactly as
  the turn left them. Anything else on top, such as an edit, a selection or a
  later turn, makes it refuse with nothing changed.
- **Framing stays off the undo stack.** Selecting a new build to frame it no
  longer leaves a "Change Selection" entry on the stack.
- **Labels get room.** An inline splice leaves room for the text a node draws
  under its tile: displayed comment lines and the prim path line.
- **Narration is separated.** Text from successive model turns starts a new
  paragraph.
- **Prompt rules.** Inspect once, then build. Do not re-query what a clean build
  receipt proves. Say so when you cannot see the viewport. State the values you
  set, not an appearance you did not observe.

**Source release for Houdini 22.0.400 / Python 3.13.** No new Windows Setup is
included. The v5.86.0 Setup contains none of the changes in v5.87.0 through
this release. Follow
[source installation](../getting-started/installation.md#source-installation),
then restart Houdini to load the updated source.

## Validation and limits

**The three requests through the panel agent, headless.** Each request ran as one panel turn in hython 22.0.400, on a fresh copy of the demo scene, with the worker built as the panel builds it, on deepseek-v4.1-flash:cloud through Ollama. On v5.91.0, with the round-3 panel changes already in the working tree, none of the three built its workflow. Scatter took 123 s and ended at the response-token limit with nothing built. The blocker took 32 s and 15 failed node creations. The render passes took 165 s and built two render ROPs and a prune instead of Render Pass LOPs. On the release code, each request ran three times, and all nine runs built the workflow:
- Scatter: 28, 28 and 34 s, with 531 instances under the camera mask each time.
- The blocker: 18, 9 and 18 s, with the key light's `light:filters` targeting a `KarmaBlockerLightFilter` prim each time.
- The passes: 14, 12 and 11 s, with two RenderPass prims each time.

In every run the new nodes had no error or warning badges, the display stayed on `demo_settings`, and the reply ended as a finished answer.

**Each recipe through the real build tool.** Each payload, with its placeholders filled for the demo scene, went through the worker's own tool path (allowlist, dispatch, handler) in hython on a fresh scene copy. All three built with no missed parameters and clean badges. Scatter produced 531 instances, with the collider mesh computing as invisible. The blocker produced a `light:filters` target of type `KarmaBlockerLightFilter`. The passes produced two RenderPass prims, the second including the lane and `/lights`.

**The current-frame read.** On a copy of the demo scene, after Configure Primitive hid the collider prim, the visibility attribute held one time sample at frame 1. Read at default time it returned `inherited`; read at frame 1 it returned `invisible`, which matched the mesh's computed visibility.

**The type hint.** Against the running build's Lop catalogue, 217 types, ranking took about 3 ms per query. Through the worker's tool path, `karmablocker` was answered with `karmablockerlightfilter` first, `gobo` with the look-it-up sentence, and a `build_graph` call with `lightfilter` with the closest real types and "Nothing was created". No node was left on the stage.

**Tests.** New test files: `tests/test_solaris_recipes.py` (22 tests, built on the queries the model sent on v5.91.0), `tests/test_type_suggest.py` (17 tests, built on its guessed type names) and `tests/test_round3_camera.py`. `tests/test_usd_relationship_aware.py` gained the current-frame read. The full `tests/` suite passed locally on Windows with Python 3.14: 10,681 passed, 482 skipped, 5 xfailed, 0 failed. On the release tree, with the tests that need a Houdini runtime deselected as CI does: 10,617 passed, 426 skipped, 120 deselected, 5 xfailed, 0 failed. The generated `emitted_node_types.json` was regenerated with its own script, which also recorded node types from earlier commits that it had not yet carried. Publication requires all six GitHub CI jobs to pass on the exact tagged commit, linked in the GitHub release.

**Limits.**
- **Scope of the runs.** The recipe runs were headless, on one model, deepseek-v4.1-flash:cloud, and on one scene. None has been recorded in the GUI yet.
- **Recipe content.** No render pass has been rendered, so the isolate pass includes the lights by reasoning, not by an image. The scatter prototype is a placeholder sphere. The collider rule follows the world importer's file naming.
- **What REVERT has been checked against.** REVERT, framing outside undo, label spacing and narration spacing are tested against fakes and have not yet been seen in the GUI.
- **Still open in the panel.** A turn that reaches the 25-round tool limit can still end mid-sentence. A response-token-limit stop is avoided because the turns are shorter, not fixed. The prompt still mentions `synapse_scout` conditionally, and the model has tried it.
- **The type hint.** Its ranking is a heuristic, and a concept that is not a node type, such as a gobo, gets no suggestion.

The inherited [v5.91.0 limits](v5.91.0.md#validation-and-limits) remain.
