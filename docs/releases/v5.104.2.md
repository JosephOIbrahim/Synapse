# SYNAPSE v5.104.2 — Connect runs no project setup

**Install this over 5.104.1.** On 2026-11-22 the first Connect after a 5.104.0 install held
Houdini's main thread in project setup until Windows closed Houdini. Why that step never returned
is still not known. 5.104.2 takes project setup out of Connect, and ending a session now queues
its session-end record instead of writing it on the thread that ended it.

**Connect, in this note,** is the MCP handshake (`initialize`) on Houdini's own `/mcp` endpoint.
The panel sends it with its first tool call, Doctor included.

This release does not fix why that step hung. The same project setup still runs on the main
thread when an agent calls `synapse_project_setup` (see [Limits](#limits)).

## What you will notice

- **Connect no longer creates the scene's notes.** Up to 5.104.1 the handshake ran
  `synapse_project_setup`, which created the scene's `claude/memory.md` and `claude/agent.usd`
  (for an untitled scene, in this launch's unsaved notes folder) and the project's
  `claude/project.md`, when they were missing. Ending an MCP session, or disconnecting from the
  fallback WebSocket server, created them too. Now neither does. The first call that writes them
  creates them: `synapse_project_setup`, a memory write or a hands-off render's task record, for
  example.
  A scene that nothing writes to gets no notes, and its sessions leave no session-end record.
- **Session-end records have an off switch.** `SYNAPSE_MCP_SESSION_END_RECORDS` is on by default.
  Set it to `0`, `false` or `off` in Houdini's environment to turn the records off. It is read at
  every session end, and read again before each scene read and each write, so turning it off also
  drops ends already queued. A scene read already posted still runs on the main thread, but its
  record is not written.
- **A record suspends only tasks created before the latest session end it names.** Up to 5.104.1
  a session-end record marked every pending or executing agent task in the scene as suspended. Now
  it marks only the tasks created before that end, counted in whole seconds: a task stamped in
  that end's own second, or with no readable stamp, is left alone (`_created_by` in
  `python/synapse/memory/agent_state.py`). The cutoff is by time only, so it covers every client's
  tasks.
- **A swept session ends at its last request.** An MCP session ends by `DELETE /mcp`, or in the
  sweep that the next handshake runs. The sweep expires a session idle longer than 30 minutes
  (`_DEFAULT_SESSION_TTL`), and while more than 100 sessions are open (`_MAX_SESSIONS`, both in
  `python/synapse/mcp/session.py`) it evicts the least recently active. A swept session's record
  now ends at that session's last request, not at the sweep. A task created after that request
  arrived, including one the request itself started, is left alone, unless the same record also
  names a later end (see [Limits](#limits)).

Which sessions get a record:

- In a graphical Houdini session, MCP session ends and disconnects from the fallback WebSocket
  server get one. The package starts that server only when Houdini's own web server adapter
  cannot load.
- The `/synapse` endpoint that Houdini's own web server serves in a graphical session writes none,
  as before.
- A server hosted in hython now writes none. Up to 5.104.1 it wrote them inline.

The full rules are in the `SYNAPSE_MCP_SESSION_END_RECORDS` row of
[DEPLOYMENT.md](../studio/DEPLOYMENT.md).

## Fixes

- **Connect makes no Houdini call and never waits on the main thread.** 5.104.0 moved the
  handshake's project-context preload onto Houdini's main thread, with a 10 s wait (the default
  `COMMAND_TIMEOUT` in `python/synapse/core/timeouts.py`). Once that work had started nothing
  could stop it, and its result was cached and never read. The handshake now creates the session
  (sweeping expired ones, whose records it only queues), clears the show-config cache and
  returns.
- **Ending a session queues its record instead of writing it on the thread that ended it.** Up
  to 5.104.1, ending an MCP session read the hip path and `$JOB` through `hou` on the web server's
  worker thread, off the main thread, then created the scene's notes and wrote `agent.usd` there.
  A fallback WebSocket disconnect did the same on its connection thread. Now that thread only
  queues the end. For the session-end record it makes no `hou` call, posts nothing to the main
  thread and writes no file but its log. One recorder thread asks the main thread for a short
  read of the scene (`run_on_main`, label `mcp:session_end:capture`) and writes the record on its
  own thread. Ends that queue together become one record. With `SYNAPSE_AUTO_MEMORY` on, a
  fallback WebSocket disconnect still waits on the main thread for one memory row (see
  [Limits](#limits)).
- **`synapse://project/context` no longer says it is auto-loaded.** Its description now ends "Not
  loaded automatically: call synapse_project_setup at session start." It names only the tool.
- **For developers: `audit_panel.py --strict` checks the model readout the panel actually shows.**
  On 5.104.1 it failed 4 checks under hython 22.0.400, because the panel shows the registry's
  display name ("Sonnet 4.6") where the audit expected `<provider>/<model>`. The readout rows now
  compare with the registry's label for the active pair and check the accessible name
  "Generation model: <provider>/<model>". A readout may elide only a label that does not fit, and
  the switch checks put the artist's engine back afterwards, even when one raises.
  Setup does not install `audit_panel.py` (the allowlist in `installer/build_payload.py`).

## Limits

- **`synapse_project_setup` still runs on Houdini's main thread and cannot be stopped once it
  starts.** The hold of 2026-11-22 began inside that same work. So a hold like it can still happen
  when an agent calls the tool, for example as its first call in a new session, instead of at
  Connect. Moving the tool's filesystem work off the main thread is remediation 2 in the
  [freeze forensics](../reviews/connect-freeze-forensics-2026-11-23.md), and it is not in this
  release. (The forensics file is in the repository; source archives leave out `docs/reviews/`.)
- **The freeze's cause is still unknown.** Two causes are still open: a `$JOB` folder inside a
  cloud-synced folder blocking one folder check on the main thread, or another thread holding
  Houdini's HOM lock. No freeze dump in the record has a stack, so neither is confirmed.
- **The forensics' other fixes are not in this release either.**
  - Freeze telemetry still names only the outer step of a nested main-thread call.
  - The emergency halt still makes a bare `hou` call off the main thread while the main thread is
    held.
  - Cancelled waiters are not woken, and still wait out their timeouts.
  - The `/mcp` server's own circuit breaker is not registered with the freeze chain.
- **Other Houdini work off the main thread remains.** It was found while this release was scoped,
  and is left for the next one.
  - `synapse_project_setup` and `synapse_memory_write` build the scene's notes outside their
    main-thread read. For an untitled scene that reaches `hou.hipFile.isNewFile()` and
    `hou.text.expandString()` on the calling thread. That thread is off the main thread when
    `synapse://project/context` is read over `/mcp`, and on the fallback WebSocket server.
  - Starting `synapse_autonomous_render` on the fallback WebSocket server reads the hip path and
    `$JOB`, builds the scene's notes and writes its task record on the connection's thread.
  - The fallback WebSocket server builds a cold bridge's memory store while it holds its client
    lock. That build waits up to 10 s on the main thread (`run_on_main`'s default), and every
    other connect and disconnect waits for it.
  - `python/synapse/server/api_adapter.py` calls `hou` off the main thread. No shipped path
    starts it.
- **With `SYNAPSE_AUTO_MEMORY` on, a fallback WebSocket disconnect still waits on the main
  thread.** For a session that ran a command, the session tracker writes its summary row through
  `run_on_main` (label `memory:add`) from the connection's thread. That wait is up to 10 s once
  posted (`_DEFAULT_TIMEOUT` in `python/synapse/server/main_thread.py`), and a timeout counts
  toward the stall detector. If the write times out or raises, the session's `memory.md` summary
  is lost as well. That disconnect's end is stamped after this wait, so its record can suspend a
  task another client created during it. The switch is off by default.
- **In a graphical session, the `/synapse` endpoint still writes no session-end record.** The
  stdio bridge (`mcp_server.py`, the repository's `.mcp.json` default) connects there, so its session
  ends leave no record. That
  endpoint is left for the next release.
- **A record is written after its session ends, so it can be lost or land elsewhere.**
  - If the main thread does not finish the short scene read within 30 s of the post
    (`_CAPTURE_TIMEOUT_S` in `python/synapse/mcp/session.py`), if the emergency halt cancels the
    read, or if Houdini exits first, nothing is recorded. Posting can itself wait for Houdini's
    HOM lock before that clock starts.
  - The record goes into the scene open when the read runs. A File > Open in between puts it into
    the newly opened scene when that scene has an `agent.usd`, and suspends that scene's pending or
    executing tasks by the same rule. For an expired session, that window opens at its last
    request and lasts more than the 30-minute session timeout. A File > New usually drops the
    record.
  - Ends that queue while a read is pending join that record, and its cutoff is the latest end it
    names. So a swept session's record can suspend a task created after that session's last
    request.
  - Two records written in the same second overwrite each other.
  - Writers of `agent.usd` take no lock. That race predates this release.
  - If writing the session entry fails after the suspension was saved, the log says the record was
    not written, but the tasks stay suspended.
- **Model-facing text still lags** (the undo-group part carried from 5.104.0). The MCP
  `initialize` instructions still describe undo-group transactions for every mutation, and still
  call the encoded light-parameter names a "Houdini 21 USD" convention.
- **`houdini_hda_promote_parm` on one component of a parameter tuple reports success but links
  nothing.** Promoting `sizex` of an internal node `box1` reports `box1_sizex`, but adds a
  three-part parameter, `box1_sizexx`, `box1_sizexy` and `box1_sizexz`, and makes no channel
  reference to `sizex` (`python/synapse/server/handlers_hda.py`). A hython 22.0.400 probe found
  it on 2026-11-23; it predates 5.104.2.
- **`audit_panel.py`, the development check, has known gaps.**
  - With pinned settings, the "model picker" row needs at least two models, so an engine with one
    model fails it. With pinned settings the readout rows also fail for an unconfigured Custom
    engine (which also fails the active engine mark), an untagged Ollama model and an unknown
    engine.
  - An exception inside the live block counts as a WARN, not a FAIL.
  - When a reading raises after the audit switched the model, only the engine is restored. With
    pinned settings the audit's model pick can then stay saved.
  - Comments in `python/synapse/panel/synapse_panel.py` still say the readout never elides, and the
    provider registry's
    `_pretty_ollama` docstring still says the audit keeps Ollama labels short.
- **5.104.1's limits still apply, with two changes.**
  - Its Connect-freeze limit is replaced by the first two limits above.
  - Its auth limit is closed. After the 5.104.1 install, `synapse_ping` answered from a fresh
    session on the seat (the owner's check, 2026-11-23). That was the end-to-end check 5.104.1's
    notes named.

  [5.104.1's limits](v5.104.1.md#limits) include 5.104.0's.
- Setup remains unsigned.

## Upgrading

1. Close Houdini.
2. Run Setup 5.104.2. This release changes no installer code and no file under `packages/`:
   `git diff --stat v5.104.1 724d766d -- installer/ packages/` is empty, and under `installer/`
   the release commit changes only the text of `installer/README.md`.
3. Restart Claude Code sessions and any SYNAPSE MCP server. A stdio bridge (`mcp_server.py`) reads
   its version when it starts, so one left running across the update has its changes refused as a
   version mismatch until it restarts.
4. If you rely on a scene's `claude/` notes existing, call `synapse_project_setup` once, or ask
   the panel what SYNAPSE remembers about the scene (its prompt tells the model to call that tool
   first).
5. To turn session-end records off, set `SYNAPSE_MCP_SESSION_END_RECORDS=0` in Houdini's
   environment.
