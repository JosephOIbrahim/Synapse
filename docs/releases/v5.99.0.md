# SYNAPSE v5.99.0

**OpenCV 5.1 can now run RETINA's change-mask chain on the GPU, locally, and
its masks are byte-identical to the CPU's.** It is off by default, and nothing
in SYNAPSE calls it in production yet.

- The chain is four steps: absdiff, a strict threshold, a morphological open
  and a morphological close. All four ran on CUDA in the qualification run.
- On all **eight** qualification fixtures the GPU mask bytes equal the CPU
  reference's: the stock `opencv-python-headless` 5.0.0.93 wheel, the owner's
  choice. The fixtures are constructed edge cases, not rendered frames, and the
  run used one workstation with one CUDA device.
- The GPU build is local. Setup does not ship it, and **no file Setup installs
  changes in this release apart from version strings.**

Producers: `harness/next-release/gpu_qualification.json` ·
`harness/next-release/gpu/qualification_profile.json` ·
`harness/vision/gpu_build_lock/build_lock_receipt.json`

## What changes

### A worker-only CUDA path for the change mask (NR-VG-RETINA-CUDA-BACKEND)

`retina/backend_cuda.py` is new. It runs the body of `retina.t1.change_mask`,
the first GPU chain the owner named (ruling R2, 2026-11-07), on OpenCV's CUDA
modules:

```
absdiff -> strict threshold -> morphological open -> morphological close
```

- **The same answer by construction.** Luma is computed on the host by the CPU
  path's own code. The threshold sent to the device is the float32 value NumPy
  itself compares at, so the device's strict `>` agrees with NumPy's. Each
  morphology step is padded on the device with that step's neutral value and
  cropped back, so the result does not depend on the CUDA filters' own edge
  rule.
- **Honest failure.** When the chain cannot run on CUDA (no usable device, a
  `cv2` build that lacks a function the chain calls, or a `cv2.error`
  part-way), `change_mask_cuda` raises `CudaUnavailable` with a reason, and
  `change_mask_check` turns that into an inconclusive check (`pass=None`) whose
  detail is the reason. It is never a pass. The module computes nothing on the
  CPU, so there is no fallback to fall into. An error that is not a
  `cv2.error` propagates unchanged.
- **Off by default, and there is no switch.** Nothing in the product imports
  the module. T1 has no production caller and no worker launches one, so its
  only consumer today is the qualification parity harness. The backend modes
  ADR-0002 describes are PROPOSED; none exists.
- **`witness()`** reports the `cv2` file, the device and the loaded native
  modules, so a qualification run records what actually ran.

Producers: `retina/backend_cuda.py` · `tests/test_retina_backend_cuda.py` ·
`harness/vision/retina_cuda_backend/backend_receipt.json`

### Three guards keep GPU code out of Houdini (NR-VG-RETINA-GUARDS)

`tests/test_retina_worker_boundary.py` adds three tests under `tests/`, which
CI collects:

- the RETINA modules that load inside Houdini (`retina/__init__.py`, `t0.py`,
  `events.py`, `exr_header.py`) cannot reach a backend module, directly or
  through another import;
- the RETINA worker tree imports no `hou`;
- the host payload ships no new RETINA module.

Each guard was made to fail on purpose first: four named mutations, every
expectation met, and the unmutated tree green before and after
(`harness/vision/retina_guards/mutation_receipt.json`:
`all_expectations_met: true`).

Producers: `tests/test_retina_worker_boundary.py` ·
`harness/vision/retina_guards/run_mutations.py`

OpenCV 5.1.0 and opencv_contrib, from pinned source commits (`e4f78fbc`,

### The RETINA venv recipe follows R4, and this is a behaviour change (NR-VG-GPU-WORKER-ENV)

`retina/requirements.txt`, `retina/setup_venv.py` and `retina/setup_venv.ps1`
now document only the worker runtime the owner ruled (R4): CPython 3.12.10
with the isolated cp312 OpenImageIO 3.1.15.0 wheel.

**If you create the RETINA venv, this changes what you can do:**

- Both scripts **refuse a hython seed**, by file name and before running it,
  and **refuse any interpreter that is not CPython 3.12**. They exit 2 and
  create nothing. Another 3.12 micro version seeds with a warning.
- An existing `retina/.venv` that is not a 3.12 venv is refused too. Re-run
  with `--recreate` (`-Recreate` in PowerShell).
- `setup_venv.ps1` now checks `$LASTEXITCODE` after every native step and stops
  with its own exit code.

This recipe is the CPU profile: it installs the stock `opencv-python-headless`
wheel and only ever writes `retina/.venv`. The GPU profile is separate
(`harness/vision/gpu_worker_env/requirements-gpu.txt`): its `cv2` is the custom
build, so it never installs an `opencv-python*` package. Both import as `cv2`,
so the two can never share a venv. The contract
`harness/vision/gpu_worker_env/worker_env_contract.json` pins the runtime, the
wheels, the recipe files and the build-lock receipt by sha256. It also records
the rule a future worker launcher must follow (set `CUDA_PATH` to the toolkit
the build used before `cv2` is imported), under ADR-0002 decision 18, which is
still the owner's to rule.

Producers: `retina/setup_venv.py` · `retina/setup_venv.ps1` ·
`harness/vision/gpu_worker_env/make_contract.py`

### The GPU equals the CPU reference on all eight fixtures (NR-GPU-QUALIFICATION)

The parity harness runs the chain over eight constructed fixtures: edges and
corners, a difference exactly at the threshold and one float32 ulp either side
of it, a non-contiguous odd-stride view, a size that is not a multiple of 16
or 32, an empty change set, and a NaN in a luma plane. It compares the sha256
of the mask bytes. The criterion is identical bytes; a difference is recorded
with coordinates and never given a tolerance.

- **The CPU reference is the owner's choice** (ADR-0002 decision 8): the stock
  `opencv-python-headless` 5.0.0.93 wheel on CPython 3.12.10 with NumPy 2.4.4,
  in its own venv. It is an independent binary from PyPI, not code this
  project built. The frozen profile (`qualification_profile.json`) holds its
  expected digests, and the closing test refuses the `cv2` 4.12.0 in the
  default interpreter's user site as an oracle.
- **The receipt** (`gpu_qualification.json`) gives the same digest for the GPU
  mask and the CPU-reference mask on every fixture, records `absdiff`,
  `threshold`, `morphology_open` and `morphology_close` dispatched on `cuda`,
  and pins the frozen profile and the build-lock receipt by sha256.
- **A third path was cross-checked, and it is not in the receipt.** The GPU run
  also computed each mask with the custom build's own CPU path, in process.
  The qualification commits (`44f8ce3b`, `186d98a0`) record identical bytes
  there too, but the committed receipt carries only the GPU and CPU-reference
  digests.
- The run was repeated on the owner's clean rebuild (`186d98a0`).

Producers: `harness/next-release/gpu/qualification/parity.py` ·
`harness/next-release/gpu/qualification/fixtures.py` ·
`harness/next-release/gpu/test_qualification_contract.py` ·
`harness/next-release/gpu_qualification.json`

## Reproduce the GPU qualification locally

This reproduces the qualification on a machine that already has the build.
The build itself cannot be reproduced from this repository alone: its
configure recipe, `Current_Configure.json`, lives in the prep project under
`E:/OpenCV5.1_Prep/02_OpenCV_Setup/preparation/`, and the build-lock receipt
records the three configure deltas and two build deltas taken against it. A
new build needs its own build lock and its own qualification (see
[Limits](#limits)). Run every command from the repository root.

1. **The CPU reference.** In a CPython 3.12.10 venv that holds
   `opencv-python-headless==5.0.0.93` and NumPy 2.4.4, and no other `cv2`:

   ```
   python harness/next-release/gpu/qualification/parity.py --mode cpu --out <cpu.json>
   ```

   It prints the identity it measured, which must equal the ruled identity in
   `harness/next-release/gpu/qualification_profile.json`.
2. **The GPU run.** In the GPU worker venv
   (`E:/OpenCV5.1_Prep/02_OpenCV_Setup/worker/py312-cuda133-worker`, CPython
   3.12.10 with the locked `cv2`), with `CUDA_PATH` set to the CUDA 13.3
   toolkit the build used (`cuda_dll_policy` in
   `harness/vision/gpu_worker_env/worker_env_contract.json`):

   ```
   python harness/next-release/gpu/qualification/parity.py --mode gpu --out <gpu.json>
   ```

3. **Assemble a receipt.**

   ```
   python harness/next-release/gpu/qualification/parity.py assemble --gpu <gpu.json> --cpu <cpu.json> --profile harness/next-release/gpu/qualification_profile.json --build-lock harness/vision/gpu_build_lock/build_lock_receipt.json --out <receipt.json>
   ```

   Compare its fixture digests with the committed
   `harness/next-release/gpu_qualification.json`. The closing tests read the
   committed receipt.
4. **Run the closing tests.** `NR-GPU-QUALIFICATION`'s predicate is
   `python -m pytest harness/next-release/gpu/test_qualification_contract.py -q -p no:cacheprovider`.
   The other four nodes' predicates are under
   `harness/next-release/proposals/predicates/`
   (`test_nr_vg_retina_guards.py`, `test_nr_vg_gpu_build_lock.py`,
   `test_nr_vg_gpu_worker_env.py`, `test_nr_vg_retina_cuda_backend.py`), and
   `graph.json` holds each exact command. The canary's predicate,
   `test_nr_vg_gpu_canary.py`, is red by design.
5. **The GPU tests.** `tests/test_retina_backend_cuda.py` runs its GPU parity
   tests only where a CUDA device is usable, so run it in the worker venv.
   Everywhere else they skip.

`parity.py` exits 0 when done, 1 when a parity mismatch or an unqualified
receipt was recorded, 2 when it refused and wrote nothing, and 3 when it could
not compute (CUDA or the CPU path unavailable; the output file says why).

## Limits

- **anthropic 2.x remains unsupported.** The model-access guard still speaks
  only the 1.x auth convention, so the pin stays `anthropic>=1.0.0,<2`. The
  migration v5.97.7 deferred to v5.98 is still unstarted.
- **Nothing calls the CUDA backend in production.** No product module imports
  `retina/backend_cuda.py`, and there is no switch to turn it on: the backend
  modes ADR-0002 describes are PROPOSED. T1 itself has no production caller.
- **No worker launches it.** Nothing launches a RETINA worker yet.
  `NR-WORKER-SUPERVISED` is the next node, and JEV parked it.
- **The GPU build is local and is not shipped.** It exists on one workstation,
  under `E:/OpenCV5.1_Prep`. Neither Setup nor the source ZIP contains it.
  Another machine needs its own build, its own build lock and its own
  qualification.
- **The qualification is narrow.** Eight constructed fixtures, one workstation,
  one CUDA device (compute capability 8.9). No rendered frame was compared, and
  no speed, memory or latency figure was measured: all of them are UNKNOWN.
- **The in-process cross-check is recorded only in commit messages**
  (`44f8ce3b`, `186d98a0`), not in the committed receipt.
- **The GPU tests skip in CI**, and on every interpreter without a usable CUDA
  device. The emulated-device parity tests need `cv2` and NumPy; CI installs
  `.[dev,websocket,mcp]` (`.github/workflows/ci.yml`), which carries NumPy but
  no OpenCV, so in CI they skip too. CI runs only the tests in
  `tests/test_retina_backend_cuda.py` that need neither a device nor `cv2`,
  among them the unavailable-path tests and the module's structural tests. This
  note found no record of the GPU tests running on a device; the GPU evidence
  is the parity run's receipt.
- **MSVC builds are not bit-reproducible here, so the receipts pin the build on
  disk.** The owner's clean rebuild of the same pinned sources, with the same
  toolchain and module list, produced eleven native files whose sha256 digests
  all differ from the first build's receipt (`ed8f88c6` against `9f67b9c5`). A
  receipt identifies the binaries on this disk, not the output of a recipe, and
  any rebuild needs a new build lock and a new qualification.
- **The binary does not embed its source commit.** The `cv2` build information
  reports version control as "unknown"; the commit identity rests on the
  source folder names and the prep project's manifest (`limits` in the
  build-lock receipt).
- **The CUDA runtime DLLs are outside the receipts.** They load at import time
  from the folder `CUDA_PATH` names and are not digested. How a launcher
  resolves them (ADR-0002 decision 18) is open.
- **Windows 26H2 vendor support is UNKNOWN.** The build ran on Windows 26H2
  under the owner's go; ADR-0002 keeps support UNKNOWN.
- **The canary is parked.** `NR-VG-GPU-CANARY` is in the graph, its predicate
  is red by design, and it waits on the worker.
- **Four of the five nodes ship by the owner's exception, not by JEV's
  order.** JEV fell back below its confidence gate and parked them; the
  exception covers this release only.
- **Owner decisions still open (ADR-0002):** 6 (CPU-reference defects a parity
  test would inherit), 7 (SSIM stays on CPU in float64), 9 (the other OpenCV
  branches), 10 (the RETINA.M3 queue entry), 11 (named owners for the
  integration, build, review and release roles), 15 (sequencing the backend
  seam against the Y change), 18 (CUDA DLL resolution), Windows 26H2 vendor
  support, and what "demo v1" means. The amendment's own `_merge_record`
  keeps OD-01 (the Grow lane), OD-04, OD-05, OD-12, OD-13, OD-16 and OD-21
  open.
- **The product-surface tool does not see `retina/`.** Its figure above counts
  none of this release's code; the file list above is the measure.
- **The backend's own docstring still calls ADR-0002 "PROPOSED, not
  ratified".** The ADR is Accepted; the docstring was not updated in this
  release.
- **Setup remains unsigned.** The interactive wizard, the registry and
  Start-menu shortcuts, and a clean-machine installation are not qualified by
  this release.
