# SYNAPSE v5.101.1

**An operator can now cap the tools the panel's model worker may use.** A new
environment variable, `SYNAPSE_WORKER_TOOL_ALLOWLIST`, takes a comma-separated
list of exact tool names. When it is set, the worker refuses every tool that is
not on the list, in every policy mode, and leaves those tools out of what it
sends to the model. The list can only remove tools; it never grants one.

**Unset or empty, nothing changes.** A seat that does not set the variable
behaves as it did on v5.101.0.

**That is the whole release.** The fixes that v5.101.0 planned for its next
release are not in it. [Limits](#limits) says where each now stands.

Every comparison in this note is against the v5.101.0 tag unless it names another
commit. The code it describes is `d7fc6b65`, the reviewed tip. The
release commits add this note, the CHANGELOG entry, the version bump, the README
and installation-guide pointers, and the crux record the tag script requires.

## What changes for an installed seat

**Two shipped code files change: `python/synapse/panel/worker_policy.py`, +20/−0,
and `python/synapse/panel/tool_bridge.py`, +9/−6.** They are the only files
`scripts/product_surface.py --diff v5.101.0 d7fc6b65` reports, and
the counts are `git diff --numstat` over the same range. Of the files that
`git diff --name-only v5.101.0 d7fc6b65` lists, they are also the
only ones that `permitted()` in `installer/build_payload.py` admits to the
payload.

**The release's version bump changes shipped files too.** It rewrites the
version string in `VERSION`, `pyproject.toml`, `python/synapse/__init__.py` and
`docs/help/index.html`. Two files the payload build generates,
`DEPENDENCIES.txt` and `payload-manifest.json`, differ in every release: both
record the version, and the manifest also records the source commit and each
file's hash.

**The two code files ship in Setup.** `python/synapse/` is in `RUNTIME_TREES` in
`installer/build_payload.py`. Apart from the version string in
`docs/help/index.html`, the documentation and tests this release changes do not
ship: of `docs/`, only `docs/help/` is in `RUNTIME_TREES`, and neither
`RUNTIME_TREES` nor `RUNTIME_FILES` names anything under `tests/`.

**What the variable does.** `active_tool_allowlist()` in `worker_policy.py` reads
it from the Houdini process's environment.

- **Unset, empty or blank: no ceiling.** A value made only of spaces and commas
  counts as unset.
- **Set: exact names, comma-separated.** Each entry is trimmed, and repeats are
  dropped. Matching is exact and case-sensitive: `SYNAPSE_INSPECT_SCENE` and
  `synapse_inspect` do not match `synapse_inspect_scene`.
- **The names are the ones the panel gives its model.** They are the registry
  names in `TOOL_DEFS` (`python/synapse/mcp/_tool_registry.py`), such as
  `houdini_create_node`, plus the six `synapse_group_*` knowledge tools.
- **An MCP client's tool list is not the panel's.** A client such as Claude Code
  shows these names with an `mcp__synapse__` prefix; the list takes the name
  without it. Over `/mcp` the client has none of the six `synapse_group_*`
  tools, and over the stdio bridge (`mcp_server.py`) it has four the panel never
  gives its model (`synapse_inspect_stage`, `synapse_scout`,
  `synapse_apply_fixture` and `synapse_remove_fixture`). An entry naming one of
  those four matches no panel tool.
- **Every unlisted tool is refused, in every policy mode:** `strict`, `standard`,
  `unrestricted`, `demo` and `proposal`. The worker leaves unlisted tools out of
  the tool list it sends to the model. If the model calls one anyway, the call is
  not dispatched, and the model gets an error with the reason "outside the
  configured worker tool allowlist", so it can re-plan.
- **It only removes tools.** For a listed tool, the decision is exactly the
  policy mode's own (`SYNAPSE_WORKER_TOOL_MODE`). Listing `houdini_execute_python`
  does not make it callable in the default `standard` mode. Under `unrestricted`,
  a listed tool stays callable.
- **It reaches the artist's own panel assistant, not only an autonomous run.**
  The interactive panel builds its model worker with the worker policy enforced
  (`python/synapse/panel/synapse_panel.py`, where it creates `ClaudeWorker` with
  `enforce_worker_policy=True`), so a set value limits the tools of the panel's
  chat too.
- **The dispatch check reads it on every call; the tool list is set per
  prompt.** The panel builds a new worker per prompt
  (`python/synapse/panel/synapse_panel.py`). It takes its tool list once, from a
  cache keyed by mode and list, and offers that list in every round; its
  dispatch check reads the variable on each call
  (`python/synapse/panel/claude_worker.py`). So a change to `os.environ` inside
  the running Houdini applies at dispatch from the next tool call, and to the
  offered list from the next prompt. A change to your Windows user environment
  reaches Houdini only when Houdini starts again.

**If your environment already sets it.** v5.101.0 does not read this variable:
`git grep SYNAPSE_WORKER_TOOL_ALLOWLIST v5.101.0` finds nothing. A seat that
already carries it gets the ceiling once v5.101.1 is installed and Houdini
restarts.

## How to use it

Set the variable in the environment Houdini starts with, then restart Houdini.
`docs/studio/DEPLOYMENT.md` names three places: your user environment, a Houdini
package, or your launcher. `INSTRUCTIONS.md` lists an edited managed package among
the cases in which Setup refuses automatic migration, so prefer your user
environment or your launcher to editing the package Setup manages.

For example, for the current Windows user, in PowerShell:

```powershell
[Environment]::SetEnvironmentVariable("SYNAPSE_WORKER_TOOL_ALLOWLIST", "houdini_create_node,houdini_connect_nodes,houdini_get_parm,houdini_set_parm,synapse_inspect_scene,synapse_inspect_node,houdini_layout_network,houdini_network_explain", "User")
```

That list is the example in `tests/test_worker_tool_allowlist.py`: node building
and the reads that support it. In the default `standard` mode all eight are
permitted, four reads and four inform-level edits, so the worker can create,
wire, set, lay out and inspect. Those edits still let it write code into a node
([Limits](#limits)). In `strict` mode only the four reads remain. Producer:
`is_tool_allowed_for_worker` for each name in each mode at `f58acb4f`; the
allowlist leaves a listed tool's decision unchanged
(`test_inside_the_list_the_mode_decides_unchanged`).

**To see the ceiling at work,** read SYNAPSE's log file, `synapse.log`, in the
folder that `SYNAPSE_LOG_DIR` names (its default is in
`docs/studio/DEPLOYMENT.md`). Each time you send a prompt, the panel's code logs
`Worker roster at send: N tools` at INFO level, where N is the number of tools
the worker sends to the model (`python/synapse/panel/synapse_panel.py`), and with
file logging on, which is the default, INFO lines go to that file.

**To remove the ceiling,** delete the variable or set it to an empty value, then
restart Houdini. If SYNAPSE's `.env` file sets it, remove the line there too:
when SYNAPSE loads, it fills an unset or empty variable from that file
(`python/synapse/host/auth.py`).

## Limits

- **A name that matches no tool is ignored, silently.** Nothing warns about it,
  no log line names it, and nothing else reads the variable:
  `git grep -n SYNAPSE_WORKER_TOOL_ALLOWLIST -- python/` lists `worker_policy.py`
  and a comment in `tool_bridge.py`. A misspelt name removes the tool you meant.
  A list in which no name is both real and permitted by the mode leaves the
  worker with no tools at all, also without a warning.
- **The list limits tool names, not what a listed tool can do.**
  `houdini_create_node` passes any node type to Houdini
  (`python/synapse/server/handlers_node.py`), and `houdini_set_parm` does not
  restrict which parameter it writes (`python/synapse/server/handlers.py`). So a
  list that holds both, as the example does, still lets the worker make a
  wrangle or Python node and write its code; `houdini_execute_vex`, which
  standard mode refuses, is itself an `attribwrangle` plus a `snippet` write in
  `handlers.py`. A listed composite builder such as
  `synapse_solaris_build_graph`, which standard mode permits, creates and wires
  nodes whether or not `houdini_create_node` is listed. This was read in the
  handlers, not run in Houdini.
- **It limits the panel's model worker, nothing else.** Only the worker's tool
  list (`get_anthropic_tools_for_worker` in `tool_bridge.py`) and its dispatch
  check in `python/synapse/panel/claude_worker.py` consult the worker policy:
  `git grep -n is_tool_allowed_for_worker -- python/ mcp_server.py` lists only
  `claude_worker.py`, `tool_bridge.py` and `worker_policy.py`. An external MCP
  client such as Claude Code, or a direct WebSocket caller, is not limited by it.
  `SYNAPSE_MCP_READ_ONLY=1` is the setting that limits those callers, to
  read-only tools. Its fence sits on `/mcp` and the `/synapse` WebSocket for
  every caller, so it also limits the panel's own worker while that worker's
  calls go through `/mcp`, and it always lets the stop controls through
  (`python/synapse/mcp/read_only_mode.py`).
- **A change to the variable while a tool list is being built can cache the
  wrong list.** `get_anthropic_tools_for_worker` in `tool_bridge.py` reads the
  variable once for its cache key (`:111`) and again, through
  `is_tool_allowed_for_worker`, for each tool it filters (`:116`). If the
  variable changes inside the running Houdini between those reads, a list
  filtered wholly or partly by the new value is stored under the old value's
  key (`:118`). From then on, while the old value is set, the worker offers the
  model that list in place of the old value's. Nothing under `python/` clears that
  cache (`git grep -n _WORKER_TOOLS_CACHE d7fc6b65 -- python/` lists its
  definition, one read and one write), so the wrong list stays until the module
  is loaded again, as when Houdini restarts. Dispatch still reads the variable on every call, so a tool
  outside the list that is set is still refused. No code under `python/`
  names the variable except to read it:
  `git grep -n -e SYNAPSE_WORKER_TOOL_ALLOWLIST -e _ALLOWLIST_ENV_VAR d7fc6b65 -- python/`
  lists its one read (`worker_policy.py:72`), the constant that names it and a
  comment. One loader can still set it without naming it: when
  `python/synapse/host/auth.py` is first imported, `_load_dotenv` copies each
  entry of the `.env` file in SYNAPSE's root folder into the environment,
  unless that variable already has a non-empty value. Finding F2 of this
  release's crux review, made with a probe that forces the change between the
  reads; the review found no stock panel setting that makes that change, and it
  did not measure whether the change ever happens on its own. Not fixed in this
  release.
- **The test scrub covers this one variable, in sessions that load
  `tests/conftest.py`.** Other `SYNAPSE_*` settings in a developer's
  environment, such as `SYNAPSE_WORKER_TOOL_MODE`, still reach any test that does
  not clear them itself.
- **The allowlist's tests leave two kinds of name unchecked.** Their every-mode
  checks walk the panel's tool list (`tests/test_worker_tool_allowlist.py:105`,
  `:110` and `:121`), which holds neither `synapse_run_recipe` nor a
  `synapse_group_*` name that no tool registers. The shipped check refuses both
  when they are unlisted, because the ceiling comes before every mode's own
  grants (`worker_policy.py:185-187`), but a later change that exempted either
  would still pass all 25 tests. Finding F1 of this release's crux review, which
  made each exemption and saw all 25 pass under both. Developer side; not fixed
  in this release.
- **The allowlist test file's import bootstrap can leave two copies of the tool
  bridge.** When `synapse.panel.tool_bridge` is imported before `worker_policy`,
  the bootstrap (`tests/test_worker_tool_allowlist.py:32-37`) removes the bridge
  from `sys.modules`, but the `synapse.panel` package keeps it as an attribute.
  The test then holds that old module and its cache, while a later explicit
  import builds a new one. It is test code and does not change dispatch.
  Finding F3 of this release's crux review, made with an import-order probe;
  whether a full suite or CI run reaches that order was not measured. Developer
  side; not fixed in this release.
- **The source ZIP still carries the account-folder paths v5.101.0's did.**

hashes.** The inspected signing setup has no publisher identity configured, so the
build produces no signed artifact. The hashes are not here because the tag is cut
after this note is final.

To check a download, compare it against `SHA256SUMS.txt`, a release asset of the
`v5.101.1` tag, and do not bypass a security warning.
