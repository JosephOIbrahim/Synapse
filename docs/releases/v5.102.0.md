# SYNAPSE v5.102.0

**This release removes or redacts paths from this project's machines in five
files that reach users.** Two files that Setup installs carried 410 paths into a
staging folder and a transcript folder on this project's machines; neither folder
is named any more. Three files in the source ZIP carried four paths into the
release machine's account folder; each now names a redaction token instead of the
account.

**No shipped code changes, so an installed seat works as it did.** Its retrieval
reads the two Setup files' new text, so a lookup that returns that text shows the
new wording. The code check:
`python scripts/product_surface.py --diff v5.101.1 1194373d` reports "no product
change" over `python`, `installer`, `mcp_server.py`, `mcp_tools_*.py`,
`install.py` and `run_panel.py`. The release's version bump also rewrites the
version string in `VERSION`, `pyproject.toml`, `python/synapse/__init__.py` and
`docs/help/index.html`, which Setup installs. The two Setup files are retrieval
text, and no
code under `python/` opens the paths they carried: `git grep -nw source_file --
python/` and `git grep -ni videodecoder -- python/` find nothing.

Every comparison in this note is against the v5.101.1 tag unless it names another
commit. The code it describes is `1194373d`, the reviewed tip. The release commits
add this note, the CHANGELOG entry, the version bump, the README's release
section, the installation guide's pointers, the release card and the crux record
the tag script requires.

## What changes

**Three source-ZIP files name a redaction token instead of the account.** In each
path into the release machine's account folder, the account name becomes
`Example`, the token the repository already uses for this. Nothing else in the
path or the file changes. In the files' bytes each separator in these paths
is four backslashes: the two paths in the `tools/` files sit in JSON nested inside
a JSON string, and the two on line 118 sit in a plain JSON string whose text
already doubled each backslash.

- `docs/SYNAPSE_MULTI_PROVIDER_LEG1_PROBE_DATA.json`: 2 paths, both on line 118.
- `tools/_hy_parity_gui.json`: 1 path, line 30.
- `tools/_hy_verbs_sweep_22.0.400.json`: 1 path, line 74.

**The SideFX Labs corpus that Setup installs no longer names a staging folder.**
In `rag/corpus/sidefxlabs_entries.json`, 409 nested `source_file` values lose a
drive letter and a staging folder and now start at `SideFXLabs`. Each change
stays on its own line (409 lines out, 409 in), so line references into the file
still resolve. Vendor default paths
in the same file, such as `C:/Program Files/...`, are unchanged.

**A reference skill that Setup installs keeps a transcript's title and drops its
folder.** `rag/skills/houdini21-reference/solaris_compound_node_anatomy.md`,
lines 145-146.

**A new test keeps these paths out of the five files.**
`tests/test_shipped_files_carry_no_owner_paths.py` fails if any of the five
files carries a path into the account folder written with any run of slashes or
backslashes between its parts, or if either
Setup file carries a path on the staging drive. Its controls show each pattern
matches a path written with slashes or with one, two or four backslashes per
separator, and spares the redaction token and other drives.

Producer for this section: `git diff v5.101.1 1194373d` over the six
paths, and the commit `1194373d`, whose rewrite asserted each count above before
it wrote anything.

## Developer side, not shipped

**The release audit now sees the spelling these paths used.** The audit of the
source ZIP is a release working-set script, not a file in this repository. Its
account pattern allowed one or two characters per separator, so it passed
v5.101.0 and v5.101.1 with the four paths inside: run on `4dc6b6e2`, the v5.101.1
tag plus one `TAGS.md` commit, it reports 0 findings. This release's audit allows any run of
slash or backslash characters, and on the same tree it reports the four paths in
the three files. It also scans the text files of the Setup payload, the payload
the Setup build record names, after checking that payload's sha256 against the
record.

**Also in this release's history, outside its crux range:** the v5.101.1 docs
commits. They made `TAGS.md` name v5.101.1, rewrote the README and the
architecture overview's diagrams, applied three wording fixes, two to
`docs/releases/v5.101.1.md` and one to the README, and updated the repository
description record in `.github/repository-metadata.json`.
Each was checked before it was pushed, and CI passed all six jobs on each of
the two pushes.

This release's crux review covers `712ca2c3..1194373d`, the lane's own commit, by Joe's ruling of 15 November 2026. The tag script refuses a record whose range holds a file that a later commit changes again (`scripts/tag_release.py:301-319`), and `README.md` changed in those docs commits and changes again in this release's commit. Codex reviewed that range and passed it on 15 November 2026; the record is `harness/notes/release-5.102.0/CRUX-RECORD.json`. It found no high or medium finding and one low one that the range did not introduce: the committed semantic index was already stale at its base. By the review's own report, its pass covers that range only, not the docs commits before it, the release commit, the release audit, Setup, a live Houdini or the other release gates.

## Limits

- **Other local paths remain in the source ZIP.** v5.101.1's crux review classed
  487 drive-rooted locations in a `git archive` of that release's reviewed tip,
  `d7fc6b65`, as recorded on this
  project's machines, in 19 files. This release removes 410 of them, all from the
  two Setup files. The other 77 remain, in 17 files that only the source ZIP
  carries; `permitted()` in `installer/build_payload.py` admits none of them to
  Setup. They include a scene path in `tools/_hy_parity_gui.json` (lines 70 and
  126), a build folder and its logs, a local corpus, a local project in three
  `docs/tops/` files and a backup destination in `.synapse/DO_NOT_FORCE_COPY.md`. [v5.101.1's Limits](v5.101.1.md#limits) lists
  all 19 files. Their removal is not planned for a named release. That review read
  only JSON, Markdown, text and log files, so 77 is a floor: Python files it did
  not read name local folders too, among them two that Setup installs,
  `python/synapse/cognitive/tools/scout.py` and `scout_ingest.py`, whose comments
  and docstrings name the local corpus folder four times
  (`git grep -n HOUDINI21_RAG_SYSTEM -- python/`).
- **The new test covers the five files only.** The release audit scans the whole
  source ZIP and the Setup payload's text files, but the only path it looks for
  is the account folder, and it matches `Users` and the account name only in
  their exact case. Neither looks for other local paths elsewhere. In the payload,
  the audit reads only files with one of its 16 text suffixes: of the v5.101.1
  payload's 1,978 files it read 1,785, and it skipped the binaries and some text,
  such as the 26 `.jsonl` corpus guides.
- **The committed semantic index was already stale before this release.** This
  release's crux review ran the semantic-index freshness check from
  `harness/verify/checks.py` on `712ca2c3` and on `1194373d`, and it failed on
  both: the digest recorded in `rag/semantic_index/manifest.json` equals neither
  tree's computed digest. The anatomy edit changes one of the digest's inputs. The
  index is not rebuilt in this release, and retrieval quality was not measured.
  Setup does not install `rag/semantic_index/`.
- **The import diagnostic's three known failures remain.**
  `python/synapse/host/daemon.py` is unchanged
  (`git diff --stat v5.101.1 1194373d -- python/` is empty). A stub `anthropic` or
  `pydantic` module without an import spec, or an import finder that raises from
  `find_spec`, replaces the diagnostic message with its own error. A local
  `anthropic.py` that shadows the package makes the message blame a dependency.
  v5.101.1's notes planned the fixes for this release; they are not in it, and no
  release is named for them.
- **The four developer-side defects v5.101.0's crux review found remain.** They
  are listed in [v5.101.0's Limits](v5.101.0.md#limits). The hardening lane that
  would fix them is deferred again.
- **Every limit of the panel worker's tool ceiling still applies.** The tool
  ceiling (`SYNAPSE_WORKER_TOOL_ALLOWLIST`) is unchanged. A name that matches no
  tool is ignored silently; the list limits tool names, not what a listed tool
  can do; it limits the panel's model worker and nothing else; a change to the
  variable while a tool list is built can cache the wrong list; and the test
  gaps v5.101.1's crux review found remain. Each is in
  [v5.101.1's Limits](v5.101.1.md#limits).
- **Leg C's uninstall-registration precondition fails on this machine.** Its
  check `production_uninstall_registration_absent_before` has failed here since
  the 2026-11-09 live install created the per-user uninstall registration.
  By Joe's ruling of 15 November 2026, the same as v5.101.0's and v5.101.1's,
  that single check failing is a known machine precondition for the v5.102.0
  Setup qualification, not a release red; any other leg C failure is a red.
  Joe's words, answering that recommendation: "All recommended".
  This release's leg C result is in its verification record, a release asset of
  the `v5.102.0` tag.
- **The suites that need Houdini.** By Joe's ruling of 15 November 2026, the
  same as v5.101.1's, this release does not measure them, and this note carries
  no seat-suite figure. Joe's words, answering that recommendation:
  "All recommended".
- **anthropic 2.x remains unsupported.** The pin stays `anthropic>=1.0.0,<2` in
  `pyproject.toml`.
- **Durable worker receipts are not in this release.**
- **Setup remains unsigned.**

## Tests

Every number here names the tree it ran on. The targeted run used CPython 3.14.2
and `python -B -m pytest <paths> -q -rs -p no:cacheprovider -m "not live"`; the
full-suite run used the same with `tests/` and `-rfEs` instead of `-rs`, so any
failure is listed by name.

- **Targeted, on the lane's files:** `tests/test_shipped_files_carry_no_owner_paths.py`
  with five more test files under `tests/`: `test_w5_cruxs1_anatomy_retrieval.py`,
  `test_w5_delta_promote_400.py`, `test_scout.py`, `test_j3_panel_formatter.py`
  and `panel/test_bc_wave.py`. Of these, `test_w5_cruxs1_anatomy_retrieval.py`
  reads the real anatomy skill and Labs corpus; `test_j3_panel_formatter.py` and
  `panel/test_bc_wave.py` read none of the five files. **63 passed, 0 failed,
  15 skipped**: 14 need PySide and 1 needs sentence-transformers. The tree was
  `712ca2c3` with the six files before they were committed; each of the five data
  files' sha256 equals `git show 1194373d:<path>`, and the test file was not
  touched between the run and the commit.
- **The new test against the old files:** the same file, run beside the five
  files as they are at `712ca2c3`, gives **5 failed, 7 passed**: the account checks
  on the three source-ZIP files and the staging-drive checks on the two Setup files
  fail, and the five control cases and the account checks on the two Setup files
  pass.
- **Full stock suite on the merge commit `29b7e906`:** **0 failed,
  12,765 passed, 727 skipped, 11 deselected, 10 xfailed** in 554 s. The merge's
  tree is the lane commit's tree, and the worktree was clean before and after the
  run. v5.101.1's own run on its release tree gave 12,753 passed and 727 skipped;
  this run has 12 more passes, and a per-file comparison of the two runs' logs
  finds the new test file's 12 cases the only difference. Producer: each run's
  pytest summary line and that comparison.
- **The audit pattern, before the release audit runs:** the widened pattern finds
  0 paths into the account folder in a `git archive` of the lane commit
  (4,057 members) and in the v5.101.1 Setup payload's 1,785 text files.
- **The release commit's own results are not in this note.** CI on all six matrix
  jobs, the build and qualification, the source-ZIP audit and the installer unit
  tests run on the release commit, which contains this note, so their results do
  not exist while it is written. They are in this release's verification record,
  `installer-verification.json`, a release asset of the `v5.102.0` tag. The tag
  waits for CI to pass on all six jobs.
