# v5.75.0 - The second write, and the silence around it

A memory store refused **every write for two days** and every health surface reported OK
throughout. This release fixes the write that caused it, disarms an unrelated data-loss
hazard found on the way, connects memory to the chat turn for the first time, and makes a
sick store visible.

## What went wrong

One logical memory-add emitted **two** records.

`session/tracker.py` deposits the rich one — `source="ai"`, with tags, `hip_file` and
`frame`. It then calls `write_memory_entry`, whose Moneta deposit writes the **same
content a second time** with every one of those fields left at its dataclass default.

They collide because the id is `sha256(content:created_at:memory_type)` at **whole-second
granularity**, so two writes inside one second share an id while carrying different
payloads. That is exactly the condition `MemoryStore._load` refuses on, and one such line
degrades the entire store and blocks every subsequent write.

Worth stating plainly for whoever touches that formula next: `created_at` was added to the
hash so *"the same content logged at different times gets distinct ids."* At second
granularity that is precisely what makes same-second writes collide. **The fix for the
previous id-collision bug is the cause of this one.** Any change has to hold both ends.

## What a reader gets

- **The duplicate deposit is gone at source.** `write_memory_entry` takes
  `deposit_to_moneta`, and the caller that already deposited passes `False`.
  `MemoryStore.add()` gains a collision guard behind it: a byte-identical re-add is a
  no-op, and a divergent same-id write routes to `update()` rather than appending the line
  that degrades the store.

- **The automatic consolidation prune no longer runs unasked.** It is now opt-in via
  `SYNAPSE_AUTO_CONSOLIDATE` and **defaults off**. It had never once fired, but it was
  live on the primary substrate with 560 records qualifying for deletion — **253 of which
  existed in only one substrate**, making their deletion permanent. Even when armed it now
  refuses unless every live record is provably mirrored. The APPROVE-gated
  `synapse_sleep_pass` path is unchanged: the capability is intact, the ambush is not.

- **Memory can reach a chat turn.** It could not before, for two independent reasons.
  `TieredRouter` was constructed without a `memory=` argument, so the tier built to answer
  from memory held `None`. And the call beneath it passed `search(text=...)` against a
  signature with no `text` parameter — a guaranteed `TypeError`, swallowed by a bare
  `except` that returned `None`. Both are fixed; the second now logs.

- **A store that is refusing writes says so.** `MemoryStore.health()` returns
  `{degraded, reason, writable, records, rejected_writes, overwrote_prior}`, consumed by the write plane,
  the panel health strip and `synapse_memory_status`. A store that **cannot answer** reads
  UNKNOWN, never OK — "we could not determine health" and "healthy" are different answers,
  and collapsing them is what produced the outage.

- **Two recovery tools, and they have been run.** `synapse.memory.primary_repair` dedupes
  conflicting identities out of a Moneta snapshot; `synapse.memory.backfill_from_moneta`
  restores records the mirror refused while degraded. Both are dry-run by default, refuse
  while a Houdini process is live or the target was touched recently, back up and verify by
  hash before writing, and re-verify by replaying the loader's own predicate afterward.

## What this release does NOT claim

- **Installing this version does not repair your stores.** It stops the cause and ships the
  tools. An already-degraded store stays degraded until `primary_repair` and
  `backfill_from_moneta` are run against it, with Houdini closed.
- **It does not change the id formula.** The whole-second collision window is still there.
  The producer that exploited it is fixed; the sharp edge is not filed down.
- **It does not fix a pre-migration plaintext store.** A store written before the
  encryption migration has zero recoverable records under any dedupe, and needs a schema
  migration instead.
- **It does not deposit mirror-only records into the primary.** The backfill reports that
  direction and deliberately does not write it; that needs `add_durable_if_absent` and the
  Moneta single-owner URI lock.

## For the repository

`9461 passed, 485 skipped, 44 deselected, 4 xfailed` on every one of the four required
contexts — ubuntu and macOS on Python 3.11 and 3.14 — measured on merge commit `ae34ed96`,
GitHub Actions run `35280154719`.

An earlier draft of this note published `9620 passed, 433 skipped, 5 xfailed` and labelled it
as the matrix result. That was a **local Windows / Python 3.14 figure**, and Windows is not one
of the four required contexts. Under this project's Law 2 every number carries a producer path;
that one named four producers that did not produce it. Corrected here rather than quietly
dropped, because the habit it comes from is the one worth breaking. `tests/test_store_incident_2026_09_17.py` pins the whole failure
class: two `add()` calls and a reload, which is all it ever took, plus the control that
keeps the `_load` detector live so green means the writer stopped rather than that the
detector stopped looking.

Adversarial review caught a defect in the first version of the fix, and it is worth
recording because it is the same class as the incident. An intermediate guard kept the
richer of two colliding records and **discarded the other while still returning the
memory id** — callers set `deposited=True` off that return. A write that silently does not
land, reported as success, is precisely the shape of the bug being fixed. It was removed --
the write is now always routed, never discarded while reporting success.

Be precise about what routing costs, though. `update()` makes the INCOMING record win, and in
this incident's own shape the incoming record is the metadata-stripped twin -- so the prior
record's tags, scene file and frame are replaced, and `add()` returns success. Bounded, because
content participates in the id and a collision is therefore metadata-only, never a lost edit.
Bounded is not absent: it is counted into `health()["overwrote_prior"]`, which every health
surface reads as NOT-green, so it cannot pass as fine.
