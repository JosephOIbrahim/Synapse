# v5.90.0 — Render returns to the panel, and the workstation profile renders on the GPU

**Render is back at the foot of the panel.** On 9/24 the footer's Render
shortcut was removed to compact the footer. Render returns as a full-width row
under the footer's unchanged 3×2 grid, with its old label and tooltip, and it
opens the same render workspace as Commands → Open the render workspace and
`/render` in the composer. The row never changes the grid's column count. Its
height comes out of the transcript, so the starting composer keeps its size.
[Rendering from SYNAPSE](../tops/RENDER_WORKSPACE.md).

**This workstation (GPU) now renders with the GPU.** The render workspace
isolates every job in a fresh runtime folder, and until now that folder also
held Karma XPU's kernel caches: OptiX's module cache and the VEX code cache in
houdini_temp. Those caches never filled from one-frame husks: reused across runs,
they still left a few kernels to compile on every frame, so XPU's CPU device
rendered every frame while the GPU waited. The workstation worker now reuses this machine's
own caches, the ones interactive Houdini and longer husk runs complete, read
from the host's environment. TEMP, APPDATA, LOCALAPPDATA and Houdini's
preferences stay isolated in the job's folder, and the worker still receives no
model or application credentials. The preview profile, This computer, is
unchanged.

**Source release for Houdini 22.0.400 / Python 3.13.** No new Windows Setup is
included. The v5.86.0 Setup contains none of the changes in v5.87.0 through
this release. Follow
[source installation](../getting-started/installation.md#source-installation),
then restart Houdini to load the updated source.

## Validation and limits

**Measured on one RTX 4090 workstation.** The demo scene's frozen frame 1
(1280×720, 64 samples) was rendered with the worker's exact environment and
husk flags. With a fresh cache, as every job had until now, it took 40.3 s and
the GPU rendered none of the samples. With this machine's caches it took 5.8 s,
the GPU rendered 64% of the samples, and no kernel compiled. Either cache alone
gave 0%, and a new cache folder kept between runs stayed at 0% over three runs.

**Through the render workspace's own service.** With this change, a two-frame
job of the demo scene driven through `FarmService` and `NativeTopsBackend`, the
code the Render view calls, completed with both frames decoded and verified:
1.6 s of render per frame, the GPU taking 59% of the samples, no kernel
compiles, and a 16.3-second render phase. The demo scene's full 120-frame arc then rendered the same way: complete, all 120 frames decoded and verified, the GPU taking 58–69% of the samples on every frame (median 62.5%), no kernel compiles, 1.5 s of render and 5.5 s of husk wall per frame, and a 13.2-minute render phase. On v5.89.0 the same profile rendered the draft move's 120 frames of this scene in 52.4 minutes, with the GPU rendering no samples on any frame.

**The Render row, checked live.** After a Houdini relaunch loading this source,
the Render row opened the render workspace on the demo scene.

**Tests.** Four tests cover the shared caches: the profile flag, the worker
environment (caches shared, everything else isolated, no key forwarded), the
host values' precedence and fallbacks, and the launch asking for them. The
Render row adds or updates tests for the footer at three widths, the editorial
footer, migration, keyboard focus and the native render workspace check's
footer route. In Houdini's own Python, hython 22.0.400, the farm tests passed: 77 passed. The full `tests/` suite passed locally on Windows with Python 3.14, with the tests that need a Houdini runtime deselected: 10,497 passed, 426 skipped, 120 deselected, 5 xfailed, 0 failed. The except ratchet is unchanged from v5.89.0. Publication requires all six GitHub CI jobs to pass on the exact tagged commit, linked in the GitHub release.

**Limits.** The caches help once a machine holds a scene's kernels. Until an
interactive Karma XPU render or a longer husk run has compiled them, frames
still render on the CPU device, as before. The GPU's share depends on the scene
and the machine; 59–64% is one scene on one workstation. Jobs now share this
machine's houdini_temp with interactive Houdini. The live Render view was not
used for the GPU measurements; they ran through its service and backend, and a
running Houdini loads this change at its next start. Under hython, 8 panel
tests failed on the Render row's tree and on a clean v5.89.0 tree alike.

The inherited [v5.89.0 limits](v5.89.0.md#validation-and-limits) remain.
