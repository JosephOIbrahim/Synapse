# v5.75.2 — The checks that could not lose

**2026-09-18.** Documentation, harness and release tooling. **Nothing that runs changed.**

Two checks this project relies on to tell the truth about a release were found unable to fail. Both are fixed, and both are now demonstrated failing on purpose, because a check that cannot lose is not a check.

---

## What changed

### A release check compared file timestamps git does not preserve

`harness/verify/hython_verbs.py` asserted that the hython verb-sweep artifact was not older than the script that produced it, by comparing `os.path.getmtime` on each.

Git records no mtimes. On a clean clone or in CI, both files take their checkout time in arbitrary order. The gate shipped one release ago and would have false-failed on the first machine that was not the one that wrote it.

The sweep now stamps a sha256 of its own source into the artifact; the verifier re-hashes the source on disk and compares. An artifact carrying no stamp is **unverifiable, and unverifiable fails** — *which script produced this* is exactly the question being asked.

**Made to lose, six ways, by an agent that did not write it:** a same-length single-byte flip mid-file in the real script, then in an isolated sandbox — stamp absent, stamp null, stamp empty, stamp wrong, wrong build pin, `complete=false`. All exit 1. It also still passes where the old rule wrongly failed: mtime inverted sixty seconds with identical content.

Two deviations are recorded rather than omitted. The hash is over CRLF-normalised bytes, because `git ls-files --eol` reports `i/lf w/crlf` on three of these files despite `.gitattributes` pinning `eol=lf`, and hashing raw bytes would have reintroduced the same false-failure class from the other direction. And the frozen baseline was **not** re-frozen: the would-be baseline differed only by an em-dash inside prose no check reads, and re-freezing a baseline over cosmetics is how a gate gets quietly weakened.

### "The product did not change" was proved with a path list blind to the MCP entry point

Every release since v5.70.1 has proved that sentence with:

```
git diff --stat v<prev> v<new> -- python installer
```

copy-forwarded into each cut's own `compose_assets.py`, and quoted in the published notes, in `CHANGELOG.md`, and inside the `installer-verification.json` that ships as a release asset.

Nineteen tracked `.py` files live at the repository root, outside both trees. Seven are the shipped MCP surface — including `mcp_server.py`, the exact file `.mcp.json` launches.

**Measured, not hypothesised.** Commit `c6221f3b`, *"asyncio.run() was disabling every MCP tool call under Houdini"*, moved 65 lines of `mcp_server.py` and nothing under `python/` or `installer/`:

```
git diff --stat c6221f3b^ c6221f3b -- python installer      ->  EMPTY
python scripts/product_surface.py --diff c6221f3b^ c6221f3b ->  mcp_server.py | 58 +, 7 -
```

The old gate reports "product unchanged" over a fix to the MCP entry point.

`scripts/product_surface.py` is now the single definition. It is importable, so this release's asset composer reads it instead of retyping a pathspec, and it **refuses a term matching no tracked file** — an empty diff from a dead term prints exactly like an unchanged tree, and git reports neither. `tests/test_product_surface.py` pins the width in both directions: too narrow loses the entry points again, too wide swallows `harness/` and reports a product change on every release.

### The README was drawing a gate that does not exist

The prompt-flow diagram showed one destructive/not-destructive branch ending in "Asks you first." **The panel does not ask.** What it has is a default-on, fail-closed DENY layer derived from gate levels (`python/synapse/panel/worker_policy.py`): a tool the worker may not call is refused with a reason and re-planned, never queued for approval. The diagram now shows three outcomes, and a new paragraph names the denied set.

The two-paths section was also on the wrong axis. Which path a call takes is decided by **how the client connected** — and the stdio server this repo configures (`.mcp.json` → `mcp_server.py`) forwards over WebSocket to the live handlers and is *not* bridge-routed despite the name, while the panel's own calls are. All four routes are now named with their files.

Emergency halt's scope is corrected from "PDG cooks under `/obj`" to cooking TOP networks under `/tasks`, `/obj`, `/stage` and `/out`.

### Three findings, no code

- **`harness/notes/findings/id-hash-collision.md`** — `ae34ed96` closed a *producer* of duplicate memory ids, not the mechanism. `created_at` is built at whole-second resolution (`models.py:147`) and the id hashes `content:created_at:memory_type` (`models.py:157-162`), so two writes of identical content and type inside one second collide **deterministically**. The live store carries `'Executed: execute_python'` 184 times with a closest repeat of 1.0s — the tightest two rows can sit without being one row. The fix already exists behind a default-off flag.
- **`harness/notes/findings/mirror-forensics-2026-09-18.md`** — four memory records, the entire v4 studio-lookdev recipe generation, exist only in the encrypted JSONL mirror. The primary has no trace of them. Recall therefore answers "Create a Solaris Network" with the v3 simple-sphere recipe.
- **`harness/notes/findings/collision-dispositions.md`** — the two known disagreeing collision dispositions are in fact four.

## Qualification

**19 of 19 PASS** against an installed Houdini 22.0.400 — a real install, upgrade, uninstall and reinstall cycle, including *"Uninstall preserves projects, memory, credentials and custom files."*

v5.75.1 shipped three assets and `qualification_report: null`; its installer was never run against a Houdini install. This release closes that.

`HOUDINI_PACKAGE_DIR` was sandboxed to an empty directory for the qualification process only — this machine registers the source tree there, which Setup correctly refuses. `discovery.py` reads `os.environ`, so nothing on the machine was changed.

## The product is unchanged, proved two ways

```
git diff --stat v5.75.1 -- python installer mcp_server.py mcp_tools_*.py install.py run_panel.py
  python/synapse/__init__.py | 4 ++--        <- the version string, and only that

payload files        1,835  (v5.75.1: 1,835)

```

Zero differing maintenance files means the embedded Python and the entire setup engine are byte-identical to what v5.75.1 shipped.

## What was NOT run, stated plainly

**The full pytest suite was not run for this cut**, and no suite figure is published in the assets. A number with no producer does not go into a release asset. The gate that did run is CI green on the four required contexts, resolved against the tagged commit by `scripts/release_ci_gate.py`.

For the same reason, the six `passing:` flags in `.synapse/contracts/hython-verbs.yaml` remain `false`.
