62 commits on top of [v5.95.0](v5.95.0.md), up to `6df72b24`, not counting these notes and the version bump. Four pieces of work: the TOPs monitor repair that v5.95.0 held back, the CTO's demo-day pass, six fixes from the improvement loop, and a Copy control on every code block.

**Three checks ran in isolated hython 22.0.400. None ran in an interactive Houdini session.** The TOPs monitor probe passed 7 of 7 scenarios, calling the handler directly. The memory runsheet's two recall lines returned the right decision on the Moneta backend, calling the handlers directly with no panel and no model. The Copy control passed 42 of 42 checks in a standalone chat display widget under offscreen Qt; the full panel was not constructed. Everything else, including the six improvement-loop items, the four phantom-name repairs and the panel's miss reporting, is tested without Houdini: with stand-in objects, source reads and the committed H22 symbol table and node catalogue.

## The TOPs monitor sees a real H22 cook

v5.95.0 listed this repair as held back. It lands here as seven commits (`6a1a673b` through `ed01db41`), all in `python/synapse/server/handlers_tops/diagnostics.py`, with a new test file.

**`tops_monitor_stream` now listens for events H22 actually sends.** At v5.95.0, `start` tried to register one handler for `WorkItemStateChange | CookProgress | CookComplete` on the graph context. On 22.0.400 `pdg.EventType` has no `CookProgress`, and its members do not combine with `|`. The error was swallowed, and the tool answered `monitoring` with no handler attached. Now each event type gets its own `addEventHandler` call:

- `WorkItemStateChange` and `NodeProgressUpdate` on every monitored `pdg.Node`;
- `CookStart`, `CookComplete` and `CookError` on one emitter: the node itself for a single TOP node, or the graph context for a network.

If any registration fails, the handlers already added are removed and `start` raises. Nothing is stored. `stop` removes each handler from the object it was registered on.

**Item events come from the nodes, not the graph context.** In the final live probe (isolated hython 22.0.400, scenario X4a), the graph context sent `CookStart` and `CookComplete` but no `WorkItemStateChange`. The two working nodes sent 40.

**Each work item is read the way H22 shapes it.** The callback reads `event.workItemId` and `event.currentState`, looks the item up with `event.context.graph.workItemById`, and takes its duration from `cookDuration`. A cached item gets a `work_item_completed` row flagged `cached`, and is counted under `cached`, not `completed`. Cancelled items get their own `work_item_cancelled` event and count.

**A failed item carries its error text.** The callback uses the event's message if it is not empty. Otherwise it takes the last 500 characters of the item's `logMessages`. In the live probe, the failing item's row carried the script's `RuntimeError: probe failure` traceback.

**`cook_state` describes the cook as it happened.** Once the monitor has received a PDG event, it reads one of six values (before that, `status` and `stop` return no `cook_state` or `last_cook`):

- `starting`: a cook began and no item has started cooking or finished yet;
- `cooking`;
- `complete`;
- `complete_with_errors`: this cook had a failed or cancelled item (H22 raises no `CookError` for an item failure);
- `error`: set by `CookError`, and it holds until the next `CookStart`;
- `nothing_cooked`.

A cook begins at `CookStart`. There are two fallbacks: the first event after `start`, when no `CookStart` has been seen, and an item entering `Cooking` after a cook that ended `complete` or `complete_with_errors`. A trailing progress tick or a dirty does not reopen a finished cook. `CookComplete` is handled once per cook.

**A generate-only pass does not erase the last cook.** H22 sends `CookStart` and `CookComplete` for a pass that only generates items. A pass in which no item entered `Cooking` or a cooked state, and no `CookError` fired, adds a `cook_complete` row that reads `nothing_cooked`. The previous cook's `cook_state` and `last_cook` stay in place. `cook_state` itself reads `nothing_cooked` only when no earlier cook exists. While such a pass runs, `status` returns `cook_state` `starting`, with the previous cook's counts in `last_cook`.

**Per-cook and lifetime counts are kept apart.** `status` and `stop` return `last_cook` (the most recent cook) next to `summary` (every cook since `start`). Both come from running counters, not from the event buffer, so trimming the buffer does not change them. Each cook's end adds a final `cook_progress` row, because H22 merges progress updates when items finish together. Progress rows report `processed` and `failed` against `total`.

**A network path watches every TOP node under it.** A path whose children are TOP nodes is monitored through every TOP node under it, inside TOP subnets too. That covers the `$render.topnet` path that the TOPs render recipe passes. The scheduler's `pdg.Scheduler` is skipped. A `pdg.Node` already in the list is skipped too, because a TOP subnet answers `getPDGNode()` with its inner node's object. A TOP node whose PDG graph context is not the first TOP node's is listed in `nodes_unmonitored` and not counted. That is how the code handles a nested topnet; no live scenario built one. `start` returns `nodes_monitored`.

**Failures that used to be swallowed are now reported.**

- The callback never raises into PDG. It keeps its first failure, and `status` and `stop` return it as `callback_error`.
- A handler that will not detach makes `stop` return `stop_incomplete` with `handler_removal_errors`. The monitor is kept, so the same `monitor_id` can retry. `force=true` drops the monitor anyway, reports `dropped_with_handlers_attached`, and gives a count of handlers still attached.
- A `stop` that fails to reach the main thread also keeps the monitor.
- A second `start` on the same path returns `already_monitoring` and attaches nothing.

`diagnostics.py` had five `except Exception: pass` blocks at v5.95.0 and has none now.

**Tests.** `tests/test_tops_monitor_events_h22.py` has 29 tests. Its stand-ins send item and progress events only through the node, as H22 does, and one test checks their members against the H22 symbol table. All 29 passed in the full-suite run on `6df72b24` (local Windows, Python 3.14, not CI).

**The live check.** `probe_v6` ran in isolated hython 22.0.400. It imported a `diagnostics.py` byte-identical to this release's (sha256 `3b16dee3…`, the same blob as `ed01db41`). **7 of 7 scenarios passed** (`probe_v6.log`, `probe_v6.results.json`, in `Downloads/synapse_night_loop/tops-20261007/probe/`):

- a fresh cook of 5 items: `complete`, 5 of 5, 100%;
- a dirty and generate with no cook: one `nothing_cooked` row, previous cook kept;
- `status` during that pass: `cook_state` `starting`, with the previous cook's counts in `last_cook`;
- a real cook of those items: `complete`, 5 of 5;
- a cook of another branch in the same network: the monitored node received no events, and its state was unchanged;
- one failing item: `complete_with_errors`, 4 completed and 1 failed, with the error text;
- a TOP subnet, in two display-flag layouts: 3 distinct nodes watched with no duplicate, 9 completed and 1 failed (matching the real item states), and every handler the monitor added gone after `stop`.

## Demo-day repairs: recall, phantom names and misses that show

This is the CTO pass for demo day, commits `ed01db41..b78abfb0`, in six merges. It covers five fix cards, four repairs of names Houdini 22.0.400 does not have, recall from natural questions, the demo's memory store kept out of git, a runsheet for the memory chapter, and a panel that shows a tool's misses. Each code change adds its own test.

**Five fix cards, four of them text.** `mcp_server.py` used to say `pip install mcp websockets`, which installs the newest `mcp`. `pyproject.toml` pins the `mcp` extra to `mcp==1.26.0`, and its comment says later versions drop the decorators the file uses. It now says `python -m pip install -e ".[mcp]"`. The README no longer calls the v5.86.0 Setup's panel "the latest". It names what needs the source install instead: Spatial, the Render footer row and the Scatter recipe that reads the scene. The installer filming plan shows `SYNAPSE-<version>-Setup.exe` (currently 5.86.0) instead of 5.67.4. The `execute_python` docstring used to say scene changes are "undo-wrapped and reversible". The code undoes one step only when the script raises one of eight error types or a subclass of one (`NameError`, `SyntaxError`, `TypeError`, `AttributeError`, `IndexError`, `KeyError`, `ValueError`, `UnboundLocalError`), and only if the undo stack changed while the group was open. Other errors keep partial work, and `atomic=False` runs with no group. The docstring now says this, calling the eight types "coding errors" without listing them. It does not mention the undo-stack check.

**A refused tool no longer points at a gate that never blocks.** That fifth card changes a message, not a document. When the panel worker refuses a review, approve or critical tool, the reason used to suggest "a bridge /mcp consent-gated call". That bridge approves everything. The reason now says the gate is outside what the panel worker may do and sends the artist to the native Houdini UI.

**Three Recipe Book recipes name nodes and parms Houdini 22.0.400 has.** `asset_structure` ended in `usdrop`, a LOP type the 22.0.400 catalogue does not list. It now ends in `usd_rop`. `trail_effect` set `traillength`, which is not a Trail SOP parm. It now sets `length`, and `result` is now 2 (Connect as Polygons) instead of 1 (Connect as Mesh), because the recipe draws lines. `bend_twist` set `bendangle` and `twist`. It now sets `bend` on the Bend SOP, and `op` 0 with `strength` on the Twist SOP. A new test checks every node and parm of these three recipes against that context's file in `rag/catalog/h22.0.400/`.

**Geometry inspection samples numeric attributes.** The sampler called `hou.Attrib.floatListData`, which the committed 22.0.400 symbol table does not list, so every numeric attribute came back with an error instead of samples. It now reads through the `hou.Geometry` reader for the attribute's class, type and arrayness: eight `{point,prim}{Float,Int}[List]AttribValues` readers, all in the symbol table. The reader table also maps the four vertex readers, but the summary lists no vertex attributes, so those four are never called. Detail attributes read through `geo.attribValue`. An attribute that is neither numeric nor string, such as a dict, reports `not sampled` instead of an error. The new tests use stand-ins that carry only the real member names.

**Recall finds a decision from a natural question.** Recall used to need every word of the question, apart from a short list of question words, to appear spelled the same in the record. "What did we decide about the hero sphere?" missed, because the record does not say *decide*. Now `SynapseMemory.recall` drops a longer list of filler and decision verbs (*decide*, *chose*, *agreed*). It folds plurals and common endings, two British spellings (*colour* and *grey*), and four small synonym groups: material/shader/shading/shade/surface, background/backdrop/cyc, fog/atmosphere/volumetric/haze/mist, and light/lighting/lit. A question about *color* is answered by any of 29 colour names. Words still match whole, so *oral* never matches inside *coral*.

**How a record qualifies and ranks.** A record must answer both terms of a two-term question, or at least half of a longer one. Words that ask for a value, like *length*, *focal* or *size*, help a record but are not required unless the question has nothing else. Records rank by the terms they answer. A term the decision line answers counts twice; a term only the reasoning or summary answers counts once. Next comes how many terms sit in the first three content words of the decision line. When two records still tie, the newer one wins, so a changed decision outranks the one it replaced when both answer the question equally. It is still word matching, with no embeddings.

**Recall refuses a subject it never recorded.** If a required term appears in no record of the kinds and tier searched, recall returns nothing instead of the nearest record. Unknown words ending in *-ing*, *-ed* or *-ly* are dropped instead, but only when every unknown word has that shape.

**Measured on recall-eval, outside Houdini, through the recall handler.** The store held 12 decisions. Every question was asked at `scope=project` and again at the default `scope=all`; the numbers here are the `scope=project` ones. On 25 held-out questions whose wording the fix's author never saw, 18 of 25 found the right decision first on jsonl and 17 of 25 on Moneta. The author did see their hit rate and miss categories between passes, and changed the coverage guard in response. None of the 5 held-out negatives found anything. The results were the same after a reopen. The shared set is not held out, because the fixes were measured against it while they were written. On that set, 60 of 65 questions hit and 1 of 20 negatives found something. Its five misses and its one false hit are pinned as expected failures, each with its cause.

**Live, at this release's commit.** An isolated hython 22.0.400 run on the Moneta backend stored five decisions, four for the project and one for the scene. It then saved, cleared the scene and loaded the hip again. Both runsheet recall lines returned the look decision first at `scope=project`, with no reference-docs row. That run called the handlers directly, with no panel and no model.

**The demo hip's memory store stays out of git.** Opening `demo/synapse_demo.hip` in place writes its memory store to `demo/.synapse/`, unless `JOB` names an existing folder above it that is not a drive root and not inside the Houdini install, in which case the store goes to `$JOB/.synapse`. `.gitignore` now lists that path, because the repo is public.

**The demo round trip runs on both memory backends.** A new test stores three decisions through the real decide handler on jsonl and on Moneta. It releases the store, opens a fresh one on the same folder, and recalls. If Moneta can be imported, the test checks that the store really is Moneta, so a silent fallback to jsonl cannot read green. In the local Windows run (Python 3.14, not CI), all 20 cases passed, Moneta's included.

**A runsheet for demo day.** `docs/DEMO_RUNSHEET.md` has a pre-flight list and the memory chapter written out in full: the exact deposit line, a primary and a fallback recall line, what success looks like and what to do when it breaks. Every recall says `scope=project`. The other three chapters are stubs.

**A tool that succeeds but reports misses reads "warn", not done.** v5.95.0 taught seventeen tools to report misses, mostly inside a success. The panel worker read only the error flag, so those calls showed a green done, and a tool whose name reads as a scene change earned a DECISION credit. `result_misses` in `core/tool_results.py` now finds them. A miss is any of these:

- a truthy `cook_error`, `settings_error`, `background_error` or `callback_error`;
- a non-empty `parms_missed`, `inputs_missed` or `handler_removal_errors`;
- `status: "error"`, or a non-empty top-level `error` string;
- a failed step in a batch's `errors` list;
- the same keys on each entry of a `results`, `passes` or `nodes` list.

**What the artist and the model see.** On a miss, the status line reads `Finished with misses: <tool> - <misses>` with a `!` glyph. The Review list flags the row instead of crediting it. The model's tool result opens with a `synapse_reported_misses` key that lists every miss. The system prompt now asks the model to name each miss before calling a step done. The result is still not an error, because the work that landed exists.

**Two smaller panel truths.** If a reply hits its token limit after some text and cuts off a tool call, the panel now names the dropped call and says it never ran. Its message also says "nothing changed in Houdini", which is true of that call only: tools that ran in earlier rounds of the same turn did land. The turn ends as truncated, not completed. **Commit to /stage** used to claim it was "routing through the consent gate", which it never raised. The chat now says the panel cannot commit yet and nothing was written.

## Six fixes from the improvement loop

Six items from the improvement loop merged into this set, from branches `rsi/loop1-*` and `rsi/loop1b-*`. Two change panel code and one changes the doctor. One rewrites a reference recipe, one corrects two doc lines, and one changes only the development harness. **None of the six was checked in a live Houdini session or against a live model provider.** Each comes with new tests: seven new files in all, two of them for the doc lines. The seven files hold 51 tests, and all 51 passed in the full-suite run on `6df72b24` (local Windows, Python 3.14, not CI).

**A failed tool call now reads as failed on every non-Anthropic engine.** A tool result carries `is_error`. The Anthropic path sends that flag as it is, but the other providers dropped it. Nemotron, Ollama and Custom share one translation into OpenAI-style tool messages, which have no error flag, so a failed call's text now starts with `ERROR: this tool call failed.` Gemini now puts a failed call's content under `error` in its `functionResponse`. On Gemini, a successful result whose payload has its own top-level `error` or `output` key, such as a result that reports a miss through a top-level `error` string, now goes under `output`, so it is not read as a failure. A success with misses gets no prefix on Nemotron, Ollama and Custom, which matches the Anthropic path.

**The usage ledger counts misses.** Each tool entry in a turn's row of `~/.synapse/usage/turns.jsonl` now has a `misses` key. For a call that returned without error, it holds the number of misses `result_misses` found in the result. A call that errored, was refused, was cancelled before it ran, or raised gets `misses: null`. A result with misses still reports `is_error: false`, so until now a call that only partly landed looked the same in the ledger as a clean one. The count stays out of the tool result the model reads.

**The TOPs reference recipe uses real 22.0.400 PDG names.** `inspect_cook_state` in `rag/skills/houdini21-reference/tops_advanced.md` can be retrieved by `knowledge_lookup` and Scout. It used names that are not in the committed H22 symbol table:

- `workItemState.Cooked`, `Failed` and `Cancelled`
- `GraphContext.workItems`
- `WorkItem.stringAttrib` and `intAttrib`

It also read `pdg_error` and `pdg_errorcount` attributes. The recipe now names nine `workItemState` members: every member in the symbol table except `Undefined`, and walks `ctx.graph.nodes()` and then each node's `workItems`. It reads attributes with `stringAttribValue` and `intAttribValue`. For a failed item it returns the whole `logMessages` log and prints the log's last line. The new tests run the recipe against stand-in objects and check every `pdg` name it uses against the symbol table.

**The semantic index was not rebuilt for that page.** The committed embedding index in `rag/semantic_index/` matched the corpus digest before this change and no longer does. The harness check `semantic_index_fresh` reads red as a result. Scout rebuilds its text corpus from the edited file, but it copies its dense vectors from the committed index, whose vector for this page was computed from the old text. Only ranking is affected.

**`synapse_doctor` checks the SideFX help library.** A new `sidefx_library` check opens the configured library through the library's own read path, `query_library("", k=0)`, which returns before any search. The check reports one of three results:

- **`skipped`** when no library is configured (no `$SYNAPSE_SIDEFX_CORPUS_ROOT` and no `.synapse/sidefx_library.json` in the repo), or when the probe itself cannot run (see Limits).
- **`fail`** when the root folder does not exist ("drive not mounted or library moved"), or when the library is unreadable for another reason, which the result names.
- **`ok`** when the library is ready. It names the generation and, where the library records them, the indexed page and chunk counts.

The doctor did not check the library before this.

**Two doc lines are corrected.** The installation page no longer says the v5.86.0 Setup has "the latest panel". It now says the Setup has the panel as of v5.86.0, and that Spatial, the Render footer row and the Scatter recipe that reads the scene need the source installation. The scene-grounding contract drops `attr.floatListData()`, which the code no longer calls. In its place it lists `attr.isArrayType()` and the `Geometry` value readers `server/introspection.py` uses (`_VALUE_READERS`).

**Rope's graph mode checks the base tree before any fix (harness only).** None of this ships into Houdini. `harness/rope/graph.py` now runs its four ratchet test files against the base tree at `init`, and before the first fixer of any run that has no recorded preflight. If any is red:

- scouts may still run, but every fix item is held;
- the run ledger gets a `PREFLIGHT` / `ratchets-red` row naming what failed;
- the status line says why.

Each new `tick` command that includes fix items re-checks a held run once. A non-zero pytest exit that names no failed test counts as red, including exit 5, where no tests ran. A timeout and a run that could not start also count as red. Before this, a ratchet that was already red on the base tree failed every fix's acceptance, so every fix was discarded. Each discard named the pytest check that failed, listing the test files in that command (the note is cut at 240 characters) rather than the failing test, and nothing said the base tree was already red before any fixer ran.

## Copy on every code block

**Each fenced code block in a SYNAPSE reply now has a Copy control.** It sits on a header row above the block, with the language label on the left and the word **Copy** on the right. Clicking it puts that block's code on the clipboard as plain text, so you can paste a snippet into a parameter by hand. Inline code gets no control, and neither do your own messages, which are shown as escaped text.

**The copy is the code as written.** Tabs, indentation and trailing spaces are kept. Only the one newline before the closing fence is dropped, a Windows `\r\n` included. The display trims whitespace from the end of the block; the copy does not.

**The control says "Copied" for 1.5 s, then goes back to "Copy".** Only that control's own text is rewritten. Two blocks with identical code share one link, so both flip together. A link that does not decode is ignored: the clipboard is left alone and a debug line is logged. `node:` and web links behave as before, and the transcript still never navigates.

**A long code line now wraps instead of widening the transcript.** The block's `white-space:pre-wrap` never reached Qt: it comes after the double-quoted `FONT_MONO_CSS` in the same `style` attribute, which closes the attribute early (see Limits). Qt then laid the block out as a plain `<pre>`, non-breakable, so one long VEX line pushed the document past the panel and the Copy control off-screen. The panel now clears that flag on every user, SYNAPSE and system message it inserts.

**Clicking Copy while the next reply streams no longer removes earlier text.** Clicking rewrites the label in place ("Copy" to "Copied" and back), which moves all later text by two characters. In the first version the stream's start was a plain number, so the streaming code deleted from an offset that was out of date. The stream's start is now tracked with a text cursor that moves when text before it changes.

**A lone surrogate character in a code block does not make the formatter raise.** The first version of the Copy link (`1f0e7136`) encoded it as strict UTF-8, which raises on a lone surrogate; v5.95.0 had no link and did not raise. The link now encodes and decodes it with `surrogatepass`.

**Live check, isolated hython 22.0.400, offscreen Qt, on a copy of the `6df72b24` tree: 42 of 42 checks passed.** Simulated mouse clicks (QTest, on the rendered controls) put a 133-character VEX block (quotes, `<`, `>`, `&`) and a 106-character Python block on the clipboard exactly. Both blocks read "Copied" and then "Copy" again after 1.5 s. A malformed link was ignored. The document stayed 418 px wide in a 418 px viewport. The probe's code lines all fit that width, and an unrelated branch tree with neither the Copy control nor the wrap fix (`e96d5bd1`, PUX-01b) also measured 418 px, so this check does not exercise a long line. A click during a stream left the transcript the same as an unclicked run once the 1.5 s had passed. The same probe on the first commit alone (`1f0e7136`) failed 8 of 42, all eight in the stream case.

**Tests.** Four new test files. In the suite run (local Windows, Python 3.14, not CI), the 36 cases in the two pure test files passed. The two files that render the widget, `tests/panel/test_copy_code_anchor.py` and `tests/panel/test_copy_code_stream_and_surrogate.py`, were skipped there because PySide6 is not installed. In that run, the rendered behaviour is covered only by the live check.

## Limits

**TOPs monitor**

- **The live probe did not use the server's own plumbing.** It called the handler directly in headless hython, with `hdefereval` stubbed, `_run_in_main_thread_pdg` run inline and `_ensure_tops_warm_standby` replaced by a no-op. It tested the monitor against real H22 PDG events, not the main-thread marshal, warm standby, the WebSocket or MCP transport, or a GUI session.
- **The final live probe used only Generic Generator items and in-process Python Script items.** No out-of-process scheduler or farm cook ran against this code.
- **Some branches are unit-tested only.** On the final code, no live scenario produced a `CookError` (so `error` and single-node `CookError` delivery are unobserved), a cancelled item, a cached item, a nested topnet in `nodes_unmonitored`, `stop_incomplete` / `force`, `already_monitoring`, a truncated event buffer, `callback_error`, a registration failure, a `stop` that could not reach the main thread, or either cook-boundary fallback. Every live monitor was started before its cook, so a cook already running at `start` was never seen live. That is the TOPs render recipe's case, because it starts a non-blocking cook before it starts the monitor.
- **The MCP tool schema was not updated.** It does not list `force`, and its description still names only started/completed/failed, `cook_progress` and `cook_complete`. A caller has to know `force` exists.
- **Return shapes changed.** `cook_progress` rows carry `processed` and `failed` instead of `completed`. `summary` adds `cached` and `cancelled`, and `total_processed` now counts all four. `status` and `stop` add `cook_state` and `last_cook` once the monitor has received a PDG event (a monitor that has received none returns neither), and `callback_error` when present. `status` adds `events_truncated` when present; `stop` already returned it at v5.95.0. `stop` alone adds `handler_removal_errors` when present, and `handlers_still_attached` when `force` drops the monitor. `start` adds `nodes_monitored` and, when present, `nodes_unmonitored`. There are new statuses: `already_monitoring`, `stop_incomplete` and `dropped_with_handlers_attached`.
- **The callback still runs on PDG's thread.** It reads `workItemById`, `cookDuration`, `resultData`, `logMessages` and every monitored node's `workItems` synchronously, and it takes a short lock for its own counters. The docstring's "does NOT block the cook thread" says more than the code does.
- **A failed item's error text is the last 500 characters of its log** when the event message is empty. It can include timestamps and lines that are not the error.
- **A network is monitored within one graph:** the graph of the first TOP node found under the path. Nodes in any other graph are listed, not counted.
- **Each path gets one monitor, and its id is derived from the path.** Monitors live only in the handler's memory. The event buffer keeps `SYNAPSE_MONITOR_EVENT_CAP` events (default 5000), and when an event arrives while it already holds more than the cap, trims to the newest 80% of the cap (4,000 by default) and flags `events_truncated`; counters are unaffected. `total` is the number of work items on the monitored nodes when the event fires, so it can change during a cook.

**Recall and the demo**

- **Recall is word matching, not understanding.** Synonyms outside its four groups still miss (aperture against f/2.8, OCIO against ACES). A word in two senses can win: "how are we lighting the scene?" returns a fog decision that says "light volumetric fog". On the held-out set, 7 of 25 questions miss on jsonl and 8 of 25 on Moneta.
- **Recall numbers come from recall-eval:** a 12-decision store, the recall handler called outside Houdini, at `scope=project`. The default scope, `all`, can merge a reference-docs row into a result, and the eval counts any such row as a miss. At `all`, 5 of 25 held-out questions found their decision first on jsonl and 4 of 25 on Moneta, and all 5 held-out negatives returned a reference-docs row. That is why the runsheet says `scope=project` on every recall.
- **The live recall check covers only the runsheet's two recall lines,** in a store of five decisions (isolated hython 22.0.400, Moneta). It called the handlers directly. No panel and no model were in the loop.
