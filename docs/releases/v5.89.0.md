# v5.89.0 — A Marble world lands metric and on its ground, and a GPU render profile

**A Marble world now lands upright, on its floor, at a named scale.** A Marble
export arrives Y-down, at a scale the file does not state, floating at the
height of the camera that captured it. The importer used to bring it in as it
was. It now adds one Transform LOP after the import, named after it with
`_ground` appended, acting on the imported world's parent prim. That node
carries the whole correction: a uniform scale, a 180-degree turn
about X for a Y-down export, and a lift that puts the floor at y = 0. The points
and the downloaded file are never changed. The display flag moves to the new
node. [World Labs import](../architecture/overview.md#world-labs-import).

**The scale always names its source.** It comes from the export's metadata when
that carries a metric scale factor. A factor of exactly 1.0 with no named source
counts as unknown. For a local file, a sidecar named `<world>.world.json` beside
it can supply `metric_scale_factor`, and it must also supply `scale_source`, a
sentence saying where the number came from: export metadata, a measurement or a
known dimension. Export metadata always wins over a sidecar. With neither, the
world is still grounded and upright, and the import says that its metric scale
is unknown.

**The floor is measured, not assumed.** When the export's collider,
`<world>_collider.glb`, sits beside it, the floor is the area-weighted densest
band of near-horizontal collider faces in the bottom quarter of the collider's
height, so window sills, ledges and steps above it cannot pull it up. Without a
collider, the densest layer of splats at the floor end is used. The import then
measures the grounded height of the splats' floor layer, and stores the whole
record with the import's provenance: the scale and its source, the offset and
its source, and that height. It reports the record in one line.

**A GPU render profile: This workstation (GPU).** The render workspace keeps
its qualified preview profile, **This computer** (Karma CPU, two threads),
exactly as it was. The new profile renders with Karma XPU and lets Houdini use
every CPU thread, under the same limits: 120 frames, 2048 pixels per side, 128
samples, 60 seconds per frame and one task at a time.
[Rendering from SYNAPSE](../tops/RENDER_WORKSPACE.md).

**One large tool result can no longer break the panel.** Reading a large array
attribute, such as the 500,000 positions of a Gaussian splat, returned every
element, 24 MB of them. That result stayed in the conversation, and every later
request exceeded the model service's size limit (HTTP 413) until the history
was cleared by hand. An array attribute longer than 256 elements now returns its
first 16 elements, its length and a note, flagged `truncated`, and for a
numeric array its per-component bounds. The panel also bounds every tool result at 96,000 characters before
it enters the conversation, and bounds a restored conversation the same way
before its first request.

**TOP cooks run again on Houdini 22.0.400.** Seven TOP tool paths called
`cook(block=...)` on a TOP node, but `hou.OpNode.cook()` takes no `block`
argument, so each one failed before a single work item cooked. They were
`tops_cook_node`, `tops_batch_cook`, `tops_cook_and_validate`,
`tops_render_sequence`, `tops_multi_shot` and both branches of
`houdini_wedge`. Each now calls `TopNode.cookWorkItems(block=...)`. The unit tests had asserted
the old call on mocks that accept any keyword; they now assert the new one.

**Source release for Houdini 22.0.400 / Python 3.13.** No new Windows Setup is
included. The v5.86.0 Setup contains none of the changes in v5.87.0, v5.88.0 or
this release. Follow
[source installation](../getting-started/installation.md#source-installation),
then restart Houdini to load the updated source.

## Validation and limits

**Checked live in Houdini 22.0.400.** A freshly started Houdini loaded this
source. A local 500,000-splat Marble export, imported through the World Labs
dialog, landed at scale 2.1362 from a known dimension: two doorways taken as
2.10 m high, measured by casting rays against the collider (the two
measurements agree within 0.5%). The ground offset was 1.2897 m, and the
measured ground height −0.016 m. Read back through USD's composed transform,
the visible floor sits within 3.7 mm of the recorded height. In the same
session, one frame of that world at 1280×720 and 64 samples rendered through
the render workspace on **This workstation (GPU)**. The job completed with its
frame decoded and verified, in a 44.6-second render phase.

**In that first job the GPU rendered none of the samples.** The render
workspace gives every job a fresh runtime folder, so Karma XPU compiled its GPU
kernels there while its CPU device rendered all 64 samples. The job then took
another 17 seconds to finish after the image was written, most likely husk
waiting on the remaining background compiles. Frames after the first in a job
share that job's folder, but a
multi-frame job has not been measured, and a kernel cache shared across jobs is
not built.

**The TOP cook fix, checked in hython and live.** Running SYNAPSE's real
handlers in hython 22.0.400, `tops_cook_node`, `tops_batch_cook`,
`tops_cook_and_validate` and both `houdini_wedge` branches returned cooked,
with work items in CookedSuccess. The two `tops_render_sequence` and
`tops_multi_shot` call sites are checked against the API only; no sequence has
been rendered through them yet. Live, `tops_cook_node` cooked a ROP Fetch whose
Karma frame was written, decoded and verified, once the scene had been saved:
an out-of-process TOP job loads the saved scene file.

**Tests.** This release adds 23 tests: 13 for the grounding arithmetic, the
sidecar and the scale rules, 5 for the workstation profile, and 5 for the
result bounds. The Houdini import test now expects the ground node and checks a
sidecar-scaled import. In Houdini's own Python, hython 22.0.400, the import,
grounding, farm and result-bound tests passed: 70 passed. The full `tests/`
suite passed locally on Windows with Python 3.14, with the tests that need a
Houdini runtime deselected: 10,493 passed, 426 skipped, 120 deselected, 5
xfailed, 0 failed. The except ratchet is at 1,360 broad handlers and 983 silent
ones, unchanged from v5.88.0. Publication requires all six GitHub CI jobs to
pass on the exact tagged commit, linked in the GitHub release.

**Limits.** The 5 cm ground tolerance used for the live check is a starting
value, not a qualified bar. The floor estimate assumes the floor is the largest
near-horizontal surface in the bottom quarter of the collider; a world where
that quarter is mostly something else, or a world with no floor, needs
inspection. The measured ground height is an independent check only when the
collider supplied the offset: without a collider, the offset and the height
come from the same splat layer, so the height is zero by construction. The
2.1362 scale is only as good as the 2.10 m doorway it came from. Authenticated
World Labs import was not exercised. The result bounds are covered by tests
but did not run in a live session. The workstation profile was measured on one
frame on one RTX 4090 workstation; its limits are the local profile's, not a
measured capacity. `tops_resume_cook` still calls `resumeCook`, which the PDG
graph context does not have on 22.0.400, so resuming a paused cook fails; it is
not fixed in this release. A TOP cook on an unsaved scene still fails without
saying why.

The inherited [v5.88.0 limits](v5.88.0.md#validation-and-limits) remain.
