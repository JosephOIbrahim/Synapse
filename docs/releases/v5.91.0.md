# v5.91.0 — One call inserts between existing nodes, and a build checks its own badges

**Insert between existing nodes in one call.** Adding nodes "after the look
node" in a chain that continues means splicing them into an input that is
already connected, and `synapse_solaris_build_graph` refused that. Now the
call references both existing nodes with `existing: true`, wires the upstream
node through the new nodes into the downstream one, and marks that last wire
`insert: true`. A splice is accepted only when the node it displaces is in the
same call and feeds the new nodes through its wires, so the stream is
re-routed and never cut; anything else is refused with nothing changed.
Without `insert: true`, an occupied input is still refused as before.

**The inserted nodes land where the chain is.** By default
(`splice_layout: "inline"`) the new nodes go directly below the upstream node,
in its column, at the artist's own spacing, and only the downstream chain in
that column moves down to make room. Every node it moved is listed with its
offset in the receipt's `layout.shifted`. `splice_layout: "side"` places them
in a column beside it and moves no existing node. The display flag is not
changed.

**A build checks what it built.** After building, the tool cooks the new LOP
nodes and reads their error and warning badges; ROP nodes are read but never
cooked, since cooking a ROP renders. An error on a node this build created
rolls the whole build back in its undo group and names the node and message;
`badge_check: false` keeps the nodes instead. An error a new node inherits from
an existing upstream node that already errors is reported as a warning, and the
build is kept. Warnings never roll back. The receipt carries `badges`.

**The build is framed for the artist.** When a Network Editor is showing the
network, the new nodes are selected and the view is framed on them with their
immediate upstream and downstream neighbours. Without a UI this does nothing,
and it never fails a build. The receipt carries `framed`.

**Scene templates keep the artist's network.** `scene_template` used to call
`layoutChildren()` on the whole network, rearranging nodes it did not create.
It now lays out only its own chain, moves it into free space below existing
content, and sets the display flag only when nothing was displayed before.

**The panel.** The system prompt teaches the one-call insertion with light
node types and parameter names verified on Houdini 22.0.400, asks for
`synapse_scout` only when that tool is available, and adds a rule for build
replies: say what was built and where, and say plainly what was not done or not
verified. The Ollama response budget rises from 4,096 to 16,384 tokens. A turn
that reaches the token limit with nothing shown now tells the artist so,
instead of ending silently. A text-only model no longer receives the viewport
capture tool.

**Source release for Houdini 22.0.400 / Python 3.13.** No new Windows Setup is
included. The v5.86.0 Setup contains none of the changes in v5.87.0 through
this release. Follow
[source installation](../getting-started/installation.md#source-installation),
then restart Houdini to load the updated source.

## Validation and limits

**Live in the panel, before the final polish.** On 10/1 at 10:58, on the demo scene in the Houdini GUI, the prompt "Light this lane for dusk: add a key light and a rim light after the look node, then show me." was answered by deepseek-v4.1-flash:cloud with one `synapse_solaris_build_graph` call carrying `insert: true` on the wire into `demo_dome`. It created `dusk_key` and `dusk_rim`, wired `look_fade_10 → dusk_key → dusk_rim → demo_dome` with the connections verified and no parameter missed, checked the new nodes' badges with no errors or warnings, and left the display on `demo_settings`. The composed stage then held `/lights/dusk_key` and `/lights/dusk_rim`. That run predates the inline placement, the framing bounds, the build-reply rule and the capture-tool change; its `framed: true` came from the earlier framing code.

**The same insertion in hython 22.0.400, on a copy of the demo scene.** With the default inline placement the build took 0.027 s. The two lights took the old `demo_dome` and `demo_cam` positions in `look_fade_10`'s column, and `demo_dome`, `demo_cam` and `demo_settings` moved down by 1.7884, two of the artist's rows, exactly as `layout.shifted` reported. The upstream nodes did not move, the display stayed on `demo_settings`, and the badges were clean. One undo restored every position, name, wire and the display. With `splice_layout: "side"`, no existing node moved.

**Refusals and rollback.** In an earlier hython run on a copy of the demo scene, before the inline placement was added, the call without `insert: true` was refused and no node name changed. A new node with an error badge rolled the build back with every node name unchanged, and inside a splice the rollback put `demo_dome`'s input back on `look_fade_10`; with `badge_check: false` the node was kept. With the look node made to error, the two new lights were kept with two inherited-error warnings. Running the same build again reported `unchanged`, with nothing created.

**Scene template on a populated stage.** In that run, `scene_template` created its six-node chain below the existing nodes, moved no existing node, and left the display on `demo_settings`. On an empty network it set the display on its `render_settings` node.

**Tests.** The three new test files hold 56 tests: the splice planner and its refusals, the badge check and inherited errors, framing with a faked editor and without a UI, inline and side placement, scene_template layout and display, the token-limit message, the capture tool following the model's vision capability, and a pin on the build-reply rule. The full `tests/` suite passed locally on Windows with Python 3.14, with the tests that need a Houdini runtime deselected, on the fix tree and again on the release tree: 10,553 passed, 426 skipped, 120 deselected, 5 xfailed, 0 failed, both times. Publication requires all six GitHub CI jobs to pass on the exact tagged commit, linked in the GitHub release.

Recorded test, 12:22 on 10/1 (OBS `2026-10-01 12-22-04.mp4`), the release tree in the GUI on the demo scene: the same prompt became one build_graph call with insert:true; the two lights landed inline between look_fade_10 and demo_dome in a straight column; the capture tool was out of the text-only model's roster (102 tools); one undo restored the chain and every position. The reply took 20 tool calls and about 90 s and said plainly it could not show a render (no vision, no render ROP); tightening that reply is open.

**Limits.** Framing with the neighbour bounds has not yet been seen in the GUI; in hython it is a no-op by design. The inline placement does not check for overlap with an unrelated node lower in the same column, and a network box around the moved nodes grows to enclose the new nodes without making them members; undo restores the box. Only the first splice in a call is placed inline. The 16,384-token budget was probed on deepseek-v4.1-flash:cloud only, not on glm-5:cloud, the default Ollama model. A token-limit stop in the middle of a tool call can still send that call with empty arguments; this is older behaviour, not changed here.

**Selection and capture.** Framing replaces the artist's selection with the new nodes, including for builds sent from an external MCP client. The capture tool is hidden from a text-only model but still allowed if it is called, and an Ollama vision model whose name is not on the known list can lose it too.

The inherited [v5.90.0 limits](v5.90.0.md#validation-and-limits) remain.
