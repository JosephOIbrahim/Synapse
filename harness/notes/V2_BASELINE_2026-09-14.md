## P2 — Main-thread dispatches per task · **ABSENT**

**Blueprint §11 (line 261):** source `synapse_tool_duration_ms` by tool. Target `1 per APPLY`.

**There is no column.** The header has exactly ten fields (line `B`), and a scan for any field
whose name contains `dispatch`, `thread`, `duration_ms` or `tool` returns the empty list (line `G`).

This is ABSENT, not zero and not unknown-per-row. The quantity was never carried into the file.

**Do not estimate it.** Round trips are not dispatches; a single model round trip can issue many
tool calls or none, and the CSV records nothing about tool calls at all.

**Smallest change that makes it measurable:** add one column fed by the metric the blueprint
already names — count `synapse_tool_duration_ms` records per task, per tool, over the task's step
window, and write the count. No new instrumentation is implied; the metric is the blueprint's own
stated source.

## P3 — Context slope across tasks · **UNEVALUABLE**

**Blueprint §11 (line 262):** context per model call (`last_prompt`), slope across tasks. Target:
flat after C3.

A slope needs task order. **The file does not carry order.** No column is a timestamp, a sequence
number or a session id (line `B`). The only time-shaped name is `wall_ms`, which is a duration, not
a clock — and it is `UNKNOWN` on all ten rows (line `F`).

**File row order is not task order.** The `task` column (line `I`) is grouped by family —
`exp`,`exp`,`exp`,`top`,`sop`,`sop`,`sop`,`ari`,`ari`,`ctx` — each family contiguous, and the
numeric suffix ascending inside every family (`exp-01,02,03`; `sop-01,02,03`; `ari-01,02`).

The families are **not** in alphabetical order — the file reads `exp, top, sop, ari, ctx`, where
alphabetical would be `ari, ctx, exp, sop, top` — so calling this a *sorted* table, as this
document's first draft did, was wrong. What the shape actually shows is **grouping**: rows
contiguous by family, suffix ascending inside each. Grouping is what a table assembled
family-by-family looks like, and equally what a run log regrouped afterwards looks like. It is
evidence that the row order is *structured*, and no evidence at all about which structure produced
it. Reproduce with `cut -d, -f1 harness/v2-20260913/artifacts/v2-baseline/baseline.csv`.

**The near-miss, stated so nobody repeats it.** `first_call_input_tokens` is non-decreasing down
the file across the nine rows that carry a value (lines `J`, `K`). That is consistent with file
order being run order. It is equally consistent with the file having been sorted by task family,
which is what the `task` column shows. A token count is not a clock — it cannot distinguish the
two, and the same nine values would appear under either story. **This inference was drawn once
already this session and refuted. P3 stays UNEVALUABLE.**

**Smallest change that makes it measurable:** carry one ordering column into each row. A source
already exists — the evidence directory holds 22 step-numbered usage files, `step13_usage.json`
through `step51_usage.json`:

```
ls harness/v2-20260913/artifacts/v2-baseline | grep -cE '^step[0-9]+_usage\.json$'    # 22
```

One of those records carries a session accumulator. Its producer path — needed because a plain
`grep '"runs"'` returns **nothing**, the JSON being escaped inside a string field:

```
grep -o '\\"runs\\": [0-9]*\|\\"tasks\\": [0-9]*' \
  harness/v2-20260913/artifacts/v2-baseline/step13_usage.json
```

That prints three lines, and all three have to be read together or the figure is misread:

```
\"runs\": 1       <- this call
\"runs\": 12      <- session accumulator, at the instant of this sample
\"tasks\": 2      <- session accumulator, same instant
```

The record carries **two different `runs` values**, so a citation of “12” that does not say
*session accumulator* is ambiguous. And `"tasks": 2` is a mid-session snapshot taken at step 13 —
it is not the ten-task total the CSV describes, and nothing here shows it ever reached ten.

Writing the step number or a task index into the CSV row is sufficient; no re-run is needed **if**
the step-file-to-task mapping can be recovered — which this document has not attempted and does
not assert.

## P4 — Cache-read share on task-first-call · **UNKNOWN on all ten rows**

**Blueprint §11 (line 263):** source `usage_sink` cache fields. Target `≥ 0.8 after G4`.

The column exists. It reads `UNKNOWN` on **10 of 10** rows (line `E`).

**This is a producer gap, not a transcription gap.** The upstream usage payload carries the fields
and they are null at the source:

```
grep -oi "cache[A-Za-z_]*" harness/v2-20260913/artifacts/v2-baseline/step13_usage.json
```

returns `cache_read` and `cache_creation`, and the surrounding text of that record reads:

```
"input_tokens": 40108, "output_tokens": 894, "cache_read": null, "cache_creation": null,
"provider": "ollama", "reported_models": [...]
```

So the schema has the fields and the emitter wrote `null` into them. Backfilling the CSV from the
existing evidence would therefore recover nothing.

**Scope of that check:** one file sampled (`step13_usage.json`). Whether every row's usage record
is null, and whether every row is the same provider, was **not** checked here.

**Smallest change that makes it measurable:** fix it at the producer, not the CSV writer — have the
usage sink record the provider's real cache fields on the task-first call, and if a provider
genuinely reports none, write that provider's name into the row so the null is attributable rather
than mysterious.
