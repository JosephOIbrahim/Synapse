Nothing, and nothing could.

5.2  But the fix is an adapter, not a subsystem

The probe sized a catalog-backed oracle at M on the belief it was new work. It is not. python/synapse/validation/catalog.py already provides the two exact lookups an IExistenceOracle needs (§2.3), pure Python, per build, degrade-safe, with rag/catalog/h22.0.400/ holding 7,862 types and their parms on disk.

A catalog-backed IExistenceOracle is a ~30-line adapter. Downgraded from M to S.

New — U5 closed, and the fix grows a second half

ConnectivityOracle is also hou-bound at module scope (host/graph_oracle.py:17). An existence adapter alone therefore leaves GraphValidator un-constructible headless, because both oracles are passed to the same constructor. The same catalog entries already carry min_inputs / max_inputs / max_outputs, so a CatalogConnectivityOracle is the same shape of adapter over the same file.

W1 is therefore two adapters, not one: S–M, not S. The value scales with it — this is the difference between "the existence check is testable headless" and "the validator is testable headless," and only the second one retires the seat requirement from the verification loop.

The one real design decision: None from the catalog means "no authority," not "does not exist." An oracle that maps None → False false-rejects; None → True false-accepts. The correct composition is: catalog answers when it has authority, live hou answers when present, and a proposal validated with neither is surfaced as unverified rather than silently VALID.

Corrected — "unverified" must not mean a new enum value in the first cut

The draft's phrasing ("stamped UNVERIFIED rather than VALID") smuggles a gated change into an ungated wave: ValidationStatus is two-valued at HEAD — class ValidationStatus(str, Enum): VALID / INVALID, cognitive/graph_proposal.py:68-70 — and graph_proposal.py is a designated gated surface (§8).
