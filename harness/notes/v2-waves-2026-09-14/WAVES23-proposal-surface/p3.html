06The apply path, re-audited

Three headline guarantees. One is asserted without evidence, one is three dispatches under a bound that abandons but does not stop, and one does not exist. The RECORD findings survived; the guarantee grades did not.

graph_builder.py = 287 lines, graph_synth_runtime.py = 176, handlers_graph_synth.py = 93, proposal_store.py = 34 (all wc -l).

Corrected — this whole section was re-graded

The draft graded the first two guarantees ANCHORED and the third REFUTED. After the apply-guarantees lens, the grades are ASSERTED, REFUTED-AS-STATED, and REFUTED-WITH-A-CAVEAT. The draft's RECORD analysis (§6.5) and its VERIFY-swallow finding (§6.4) were attacked and held — both are confirmed correct, and §6.4 got worse on inspection, not better.

6.1  One undo group — asserted not anchored

The code shape is right. with hou.undos.group(undo_label): at graph_builder.py:126, wrapping create → set parms → connect → read-back (:131-159). Exception path destroys only NEW nodes, still inside the group, returns a structured FAILED (:160-183).

The evidence is not.

Refuted — "one artist Ctrl+Z reverses the whole build" is not evidenced anywhere

graph_builder.py:196 emits revert=f"single undo reverts: '{undo_label}'" unconditionally, with no check that undos are enabled. The file contains zero hou.undos references other than the group itself.

The sibling path already solved this. shared/bridge.py:1662-1677 derives undo_group_active from hou.undos.areEnabled() plus undoLabels snapshots around the group, and explicitly enumerates the "under a hou.undos.disabler() scope or a zeroed undo memory" case. The pattern exists, in-tree, and was not applied here.

The pinning test is mock-deep, not evidence-deep. tests/test_graph_builder_mile3.py:113-126 defines a hand-rolled _FakeUndos/_FakeUndosGroup with no areEnabled, installed at :167. Scenario 2 (:292, "the whole build is wrapped in EXACTLY ONE undos.group") proves the call was made — not that an undo entry exists, and not that one Ctrl+Z reverses it.

The file concedes it. graph_builder.py:13-14: "GUI undo/consent, typed VOP wires, and production provenance are not qualified by these fixtures." The draft quoted that caveat in §10 and still graded §6.1 ANCHORED. The caveat and the grade cannot both stand; the grade goes.

Replacement: the guarantee is ASSERTED — code shape confirmed, effect unverified. W5 ports the bridge's evidence derivation so revert= is emitted only when a group was actually recorded, and the GUI Ctrl+Z check in §10 becomes a gate on the grade rather than a nice-to-have.

6.2  One main-thread dispatch — refuted as stated

run_on_main(_on_main, label="graph_synth:_handle_instantiate_graph") at handlers_graph_synth.py:93. graph_builder itself does no marshalling; the handler owns it. Registered as instantiate_graph at handlers.py:860. That much is true. Two things around it are not.

(a)  It is three dispatches, not one

A live-path mutating command gets two additional main-thread dispatches bracketing the handler's one: integrity_envelope.capture_scene_hash calls run_on_main per capture (server/integrity_envelope.py:205-225), and handlers.py:521-529 places the capture pair inside the C5 mutation lock bracketing the op. instantiate_graph is not in ENVELOPE_SKIP_COMMANDS (integrity_envelope.py:80-99), and envelope suppression only fires when bridge-routed (:137-146) — which the live /synapse path is not.

The envelope file prices this itself at :124-134: "if T1 is real, the two capture hops per mutating op become a measurable latency tax." Each hop is bounded at 1.0s (:172) and returns honest None on miss, so this is a bounded tax, not a hang. But any latency claim about apply must count three wakes, and the shed lever is SYNAPSE_LIVE_ENVELOPE=0 (integrity_envelope.py:132-134).

(b)  The bound abandons the payload without stopping it — and a retry double-builds

Refuted — the highest-severity finding in the crucible, and it is silent

handlers_graph_synth.py:93 passes no timeout, so the apply runs under _DEFAULT_TIMEOUT = 10.0 seconds (producer, re-run this pass: grep -n "_DEFAULT_TIMEOUT\|_SLOW_TIMEOUT" python/synapse/server/main_thread.py → 21:_DEFAULT_TIMEOUT = 10.0, 22:_SLOW_TIMEOUT = 30.0).

The C4 abandoned-flag machinery only no-ops payloads that have not started — main_thread.py:564 sets started[0] = True before fn(). The file names the residual itself at :536-538: "A payload already inside fn() when the timeout fires is the accepted residual race… if the deferred payload later runs fn() anyway, that mutation is a zombie applied after the failure report (and a retry then double-applies)."

Nothing makes apply idempotent. ProposalStore.get() does not consume — it returns entry[1] and leaves the entry in place, TTL 1800s, no built-marker (producer: full read of python/synapse/host/proposal_store.py, 34 lines). TOCTOU re-validation of an all-NEW proposal still returns VALID against a scene that now contains a copy. So a retry after a timeout builds the graph twice, in two undo groups.

Why 10s is not obviously generous: inside that one payload sit a full live-hou GraphValidator re-validation (graph_synth_runtime.py:53-62 — HouExistenceOracle per node and per parm), createNode with init scripts per node, parm sets, setInputs, read-backs, then _agent_usd_provenance (graph_synth_runtime.py:96-127) opening and writing a USD stage under $HIP. That nested work is unbounded, because run_on_main fast path 1 returns fn() directly with no timeout when already on main (main_thread.py:474-475).

The only existing mitigation is prompt text. panel/tool_executor.py:738-746 and panel/claude_worker.py:560 emit "may STILL be running inside Houdini — do not retry." That is a sentence shown to a model in the panel. The /mcp client never sees it.

Replacement: this becomes W4 in §9 — either give instantiate_graph _SLOW_TIMEOUT and report overrun as UNKNOWN rather than FAILED, or make apply idempotent at the store (consume-on-build, or a built-marker keyed by proposal_id) so a retry after a timeout is a no-op. Reachability of the 10s bound is unmeasured — see §12.4 and G5. The defect does not depend on the answer.

6.3  One cook — refuted, with one caveat the draft missed

Grep for cook across graph_builder.py, graph_synth_runtime.py, and handlers_graph_synth.py: zero hits (exit 1). No .cook(force=True), no .cook(block=…), no cookCount read.

parm.eval() / tup.eval() (graph_builder.py:245, :250) force evaluation of a single parameter expression — not a node or network cook.

Dozens of .cook( calls exist elsewhere in the tree (handlers_usd.py, handlers_material.py, handlers_node.py, handlers_cops.py, handlers_tops/*), so the pattern is established everywhere except here.

Corrected — the refutation, and the fix it prescribed

On the refutation: "zero grep hits for cook" proves the apply path never requests a cook. It does not prove none fires. parent.createNode (graph_builder.py:133) runs node init scripts by default and parm.set (:244) fires authored parm callbacks — both are documented Houdini routes to cooks and to further node creation. Restated: no requested cook; implicit cooks via init scripts and parm callbacks are unaudited.

On the fix: the draft prescribed "an explicit cook of created leaf nodes inside or immediately after the undo group." That is unsafe as written, two ways. (1) A cook inside the group lands inside the try: at :128, so a benign cook error — a file SOP with an unresolved path — raises, hits the except at :160, destroys every created node, and returns FAILED. A cook error would nuke a structurally correct build. (2) A forced cook is unbounded work landed inside the 10s dispatch bound of §6.2(b) — the same class as the documented render freeze (executeInMainThreadWithResult into node.render()).

Replacement in §9 (W7): recon first (G3 as a pure measurement, not a gate), then cook after the group closes and outside the try, bounded, with "built, cook incomplete" as a distinct status rather than a failure. Size holds at S; the design was the defect, not the effort.

6.4  What VERIFY does with an unreadable value

It collapses UNKNOWN into None, indistinguishable from a legitimately-None observed value. _set_and_read (graph_builder.py:236-251) initialises the record with observed: None and overwrites it only if node.parm() or node.parmTuple() resolves. A proposal naming a parm that does not exist on the created type yields {requested: <value>, observed: None} — with no flag anywhere, and InstantiationResult.errors is populated only on HALT re-validation issues, never on BUILT (graph_builder.py:51, :114, :189-197).

The wire read-back is accurate by contrast: _read_connection (graph_builder.py:253-268) reports wired: False when the live scene does not show the connection.

Corrected — two axes, and the draft only measured one

The draft said "half of VERIFY is honest and half is silent," and prescribed resolved: bool as an S. The record-accuracy half of that is right and holds. The missing half is consumption, and it is worse than the draft implied:

  • wired: False changes nothing. Status is still InstantiationStatus.BUILT, ok() returns True (graph_builder.py:53-54, :189-197), errors stays empty on the BUILT path (:51), and result_to_dict passes the records through verbatim (graph_synth_runtime.py:147-160 — citation corrected from :145-158).
  • Grep across python/synapse finds no consumer of parameters_set and no consumer of connections[*].wired. Nothing compares requested against observed anywhere.
  • The sibling subsystem does exactly that comparison and fails on it — recipes/verify.py:646, "requested values not observed." The pattern was available and not applied.

So an apply where every connection failed to wire and every parm was unreadable returns BUILT / ok=True with a cheerful message.

Replacement: W6 keeps resolved: bool and adds the part that makes it mean something — any wired: False, or any unresolved parm, must downgrade the status (a PARTIAL state) or populate errors on the BUILT path. Otherwise the new flag is one more field nobody reads. Size moves S → S–M.

I accept the substance and contest one word of the framing — see §12.3. An accurate-but-unconsumed record is not dishonest; it is inert. The two failures need different fixes, and collapsing them hides that.

6.5  What RECORD writes, and whether anything reads it

Held — attacked and confirmed, to the byte

The provenance counts reproduce exactly on an independent re-run: 5,001 directory entries of which one is a .tmp (hence "5,000 of 5,001 parsed"), 57 instantiate_graph, 65 propose_graph. The channel analysis below was not contradicted anywhere.

Two independent channels. One is silent-failable; the other is content-free.

Channel A — agent.usd decision narrative (silent-failable)

_emit_provenance (graph_builder.py:270-287) writes {decision, reasoning, parent_path, created_paths, model_id, revert} — the human-readable record, the one that says what was built. It is live-wired: graph_synth_runtime.py:142 constructs GraphBuilder(…, provenance_writer=_agent_usd_provenance), and that writer (graph_synth_runtime.py:96-127) appends into $HIP/claude/agent.usd → /SYNAPSE/memory/decisions via agent_state.log_decision (memory/agent_state.py:549-573).

Channel B — FloorGate Tier-0 (always fires, records digests only)

CommandHandlerRegistry.invoke() wraps every registered command through FloorGate.wrap (handlers.py:387-404); instantiate_graph is registered (handlers.py:860) and is not in _READ_ONLY_COMMANDS (40 names, handlers.py:204-245), so it is classified mutating and gets a record.

This fires for real. A sample record read off disk (.synapse/provenance/op-20260913T213803174370Z-000002.json):

{ "op": "instantiate_graph", "op_id": "op-20260913T213803174370Z-000002",
  "origin": "handler", "outcome": "ok", "parent": null,
  "payload_digest": "60194c93…", "result_digest": "1d6533…",
  "session": null, "ts": "2026-09-13T21:38:03.174965+00:00" }

57 such records exist, with outcomes {ok, error} (producer: scan of .synapse/provenance/*.json matching op == "instantiate_graph").

But it records digests, not content. A human reading that record learns that an instantiate happened and that its result hashes to 1d6533…. They cannot learn what was built, which nodes, which parms, or whether the parm read-back matched. It is tamper-evidence, not an audit trail. session is null, so records are not grouped by session either.

Readers: FloorGate provenance is read by exactly one consumer — server/doctor.py:857-866, which bundles the newest 3 files into a diagnostic zip. memory/ledger.py:222 only mirrors its path-resolution logic. .synapse/ledger/ holds 29 files, all science-harness kinds (19 Confirmation, 4 DocConformance, 3 Deferred, 1 DeadEnd, 1 SubstrateAssumption) — unrelated to instantiate.

So: RECORD writes 5,001 files (producer: ls .synapse/provenance | wc -l), and the only thing that reads them is a support bundle. No artist-facing read, no query, no verification surface.

The InstantiationResult — which does carry the reviewable content (created_paths, parameters_set, connections, revert, errors; graph_builder.py:43-51, serialized at graph_synth_runtime.py:147-160) — is returned to the WS caller and persisted nowhere the artist can re-read it.
