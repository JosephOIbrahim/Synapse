7.2  The smallest correct change

The change the brief asks for already shipped in 8c23fccc — instantiate has its row, it maps to build_from_manifest, and build_from_manifest is review (shared/constants.py:93). That is correct: the host may (with consent), the worker may not (worker_policy.py:178-179).

The draft then proposed adding "propose_graph" to _READ_ONLY_COMMANDS as "one line." The justification for the intent is still written in three places in the tree — TOOL_DEFS marks it read_only=True (_tool_registry.py:1391); its handler docstring says "Read-only — it validates + parks, it does NOT mutate the scene" (handlers_graph_synth.py:40-42); its tool description says "Mutates nothing" (_tool_registry.py:1384). The mechanism is not one line, and one of its side effects is harmful.

Refuted — "proposals validate during renders" was the draft's whole leverage, and it does not follow

The draft ranked this change #1 of nine on the claim that it unblocks proposal validation during a render. Dropping the C5 lock frees the lock, not the main thread.

_handle_propose_graph marshals with run_on_main (handlers_graph_synth.py:69) because its grounding is a live hou oracle and "MUST run in the Houdini process" (module docstring). _handle_render marshals for the same reason (handlers_render.py:628-631: "Marshals via run_on_main since hou.RopNode.render() must run on the main thread"). For any render that occupies the main thread, a reclassified propose still queues on the marshal — same wait, different queue.

The precedent does not transfer. handlers_render.py:1677-1681 justifies render_stop/render_farm_cancel as read-only because "They mutate no scene state and create no undo entry — they signal an OS process" — they are main-thread-independent (rps/rkill against background processes). propose_graph is main-thread-bound by construction.

And the draft's own test could not have caught this. "A propose dispatched off-main while _MUTATION_LOCK is held by another thread returns without blocking" passes after the change, but it proves lock-freedom and is silent on main-thread contention — it cannot fail for the reason the benefit was claimed.

Replacement: the unblock survives only in the narrow case of a background or farm render that holds the C5 lock without occupying the main thread. Stated unconditionally it is false, so it is stated conditionally in W8, and W8 loses its #1 rank to the two items that genuinely retire a seat requirement.

What the misclassification still costs today, per propose call — the two surviving items:

  1. It takes the C5 mutation lock (handlers.py:509-520), so a background/farm render holding that lock blocks proposal validation for its whole duration.
  2. It captures a live integrity envelope — two topo scene hashes bracketing an op that changes nothing (§6.2a).
  3. It writes a false mutation record — 65 of them on disk (§6.6, L3-5). And the obvious remedy also deletes the only record there is.

7.3  The structural question: can the policy table express "host may, model may not"?

Only by accident, and the escape hatch proves it.

OPERATION_GATES is dict[str, str] — operation → risk word. One axis. Audience is not a column.

"Host may, model may not" is expressible today only because two consumers happen to read the same value in opposite ways:

  • the bridge reads review as "propose, log, continue unless rejected" (shared/bridge.py:2471-2473)
  • worker_policy reads review as "hard deny" (worker_policy.py:64, applied :224)

So risk level is being overloaded as an audience proxy. Three pieces of evidence that the table cannot carry the axis:

  1. The inverse need required a hand-maintained frozenset outside the table. _WORKER_BUILDER_ALLOWLIST (worker_policy.py:76-79) re-permits two review-gated composite builders to the worker, with a 10-line rationale comment. If the table could express audience, that allowlist would be a column value.
  2. A third audience required a new code branch, not a table edit. The proposal mode is 19 lines of branching (worker_policy.py:162-180), not a row.
  3. The same missing row means opposite things to the two consumers. For the 16 mutating tools with no _TOOL_TO_OPERATION row (cops_create_copnet, houdini_create_point_instancer, houdini_set_payload_loadstate, houdini_set_usd_primvar, houdini_shot_render_ready, synapse_doctor, synapse_emergency_halt, synapse_render_farm_cancel, synapse_render_stop, synapse_solaris_component_builder, synapse_solaris_create_variants, synapse_solaris_import_megascans, synapse_solaris_scene_template, synapse_solaris_set_purpose, synapse_write_report, tops_monitor_stream): worker_policy fails closed and denies (worker_policy.py:230-231), while bridge_adapter fails open to set_parameter = inform (bridge_adapter.py:361). One absence, two opposite defaults.

That is bigger than a missing row, and bigger than the instantiate question. It means:

  • Any op that is genuinely low-risk for the host but must not be model-initiated has to be branded high-risk at the host too — so the host pays a consent ceremony for it. Applying an already-human-reviewed proposal is exactly that op. If the C1 hunk card is the approval, then a review gate on instantiate_graph is a second approval of the same decision. Double-gating is the structural cost of a table with no audience axis — and it is a cost the hunk card ships with until the gated wave lands (annotated on W10, W11, W12 in §9).
  • Adding a per-engagement audience (C7) cannot be a table edit. It is a new dimension.

The honest statement: the policy table cannot express "host may, model may not." It expresses risk, and two consumers interpret risk as audience in ways that happen to be right today and required a hardcoded allowlist the one time they weren't.
