### The finding the blueprint did not anticipate

`charmander`/`charizard` are **not only identifiers — they are persisted USD
metadata values** (`scene_memory.py:476,487` writes `"evolution": "charmeleon"`).
Deleting the reader deletes the ability to open memory written by any prior
session. This is a **data-migration problem wearing an identifier-cleanup
costume.**

**Disposition:** rename the *surface*, keep the *reader*, migrate the *data*.
Nothing in the audit supports a straight `git rm`.

## B · `synapse_evolve_memory` / `approval_token` / `target_stage`

Commands:

```

```

| Path | Role |
|---|---|
| `python/synapse/mcp/_tool_registry.py:1155` | Tool registration — **public API surface** |
| `python/synapse/server/handlers_memory.py:337-430` | Live handler; `target_stage=="charizard"` → `apply_consolidation` |
| `python/synapse/memory/consolidation.py:151-410` | `approval_token` bound to a specific dry-run plan; apply refuses without a matching token |
| `shared/evolution.py:114,141` | `target_stage` on the legacy check result |
| `tests/test_w3_evolve_consolidation.py` | Pins the whole path |

### Reframe

The blueprint calls `approval_token` a "manual approval-token gate" to be
deleted under the zero-LLM / no-human-token law. Read the code: it is **not** a
human consent prompt. It is a **plan-binding nonce** — a dry-run computes a
consolidation plan and hashes it; apply refuses unless the caller hands back the
token for *that* plan (`consolidation.py:343-351`). It exists to stop a stale
plan from mutating a store that moved underneath it.

That is a **compare-and-swap**, and it is the correct pattern. Removing it does
not remove a human gate; it removes optimistic-concurrency control from the only
destructive memory operation in the product.

**Disposition:** keep the mechanism, rename it (`plan_token` / `plan_etag`), and
drop the misleading word "approval". The *interactive* part to remove is the
`REVIEW`-gated `evolve_memory` verb, not the CAS token.

## C · Single-handle enforcement — the real state

Command:

```
git grep -n "storage_uri" python/
git grep -n "^_MONETA_STORE\|^_global_synapse\|^_STORE" -- 'python/**/*.py'
```

**There is no missing singleton. There are two competing ones, and one of them
is not thread-safe.**

| Authority | Path | Key | Lock | Closes prior handle |
|---|---|---|---|---|
| Ledger store | `python/synapse/memory/ledger.py:320-437` | `abspath(ledger_dir())` | ✅ `_MONETA_LOCK` | ✅ yes |
| Global memory | `python/synapse/memory/store.py:1514-1522` | *(none — process-global)* | ❌ **none** | ❌ no |
| Proposal store | `python/synapse/cognitive/tools/propose_graph.py:31` | injected | n/a | n/a |

`get_synapse_memory()` is an unlocked check-then-create:

```python
if _global_synapse is None:
    _global_synapse = SynapseMemory()
```

Two threads entering together construct two `SynapseMemory` objects. One wins
the module global; the other is orphaned **while still holding a Moneta handle**
on the same storage dir. `ledger.py` gets this right 1200 lines away in the same
package.

**This is the highest-value unblocked defect the audit found.** It is precisely
the failure the blueprint's "Single Handle Enforcement" law targets — and the
blueprint's proposed fix (a singleton inside `MemoryPort`) would add a **third**
authority in a module that nothing currently calls, leaving both real ones
untouched.
